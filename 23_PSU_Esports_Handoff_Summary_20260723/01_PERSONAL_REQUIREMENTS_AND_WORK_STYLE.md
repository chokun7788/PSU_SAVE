# Personal Requirements And Work Style

ไฟล์นี้สรุป requirement ประจำตัวของผู้ใช้ที่ต้องรักษาไว้เมื่อรับช่วงโปรเจกต์นี้

## ภาษาและสไตล์การตอบผู้ใช้

- ตอบผู้ใช้เป็นภาษาไทย
- ตอบตรงประเด็น ไม่เวิ่นเว้อ
- ใช้ answer-first style เสมอ:
  - ตอบคำตอบหลักก่อน
  - แล้วค่อยให้รายละเอียด แยกหัวข้อ หรือแหล่งข้อมูล
- ถ้าเป็นรายการหลายข้อ ให้ใช้ bullet `•`
- ถ้ามีหัวข้อใหญ่และหัวข้อย่อย:
  - หัวข้อใหญ่ใช้บรรทัดแยก
  - bullet ชั้นแรกใช้ `•`
  - bullet ชั้นในใช้ `◦`
- คำตอบ chatbot ที่ออกสู่ user ควรสุภาพ กระชับ อ่านง่าย และดูเหมือน chatbot ใช้งานจริง
- ถ้าเป็นข้อมูลของ PSU Esports Studio - Phuket ต้องอ้างอิงข้อมูลจริงที่มีในระบบ
- ถ้าไม่มีข้อมูลจริง ห้ามเดา ให้ตอบ no-answer แบบสุภาพ
- ถ้าคำตอบมาจาก rulebase/fast path/structured/RAG ห้ามบอกว่าเป็น LLM
- อย่าอธิบายภายในให้ user ทั่วไปเห็น เช่น “ระบบใช้ RAG” เว้นแต่ผู้ใช้กำลัง debug ระบบ

## วิธีทำงานกับผู้ใช้

- ผู้ใช้ต้องการประหยัด token:
  - อย่าอธิบายยาวเกินจำเป็น
  - ไม่ต้องบอกทุกครั้งว่าเขียน daily log แล้ว
  - ไม่ต้อง list test ทั้งหมดใน final ถ้าไม่ได้ถาม
  - ถ้าทำเสร็จให้สรุปเฉพาะสิ่งที่เปลี่ยนและผลลัพธ์
- ผู้ใช้ชอบให้ทำจริง ไม่ใช่เสนอเฉย ๆ ถ้าคำขอชัดเจน
- ถ้าเจอปัญหา ให้บอกตรง ๆ ไม่อวยระบบ
- ถ้าไม่แน่ใจว่า route ไหนตอบผิด ให้ตรวจ mode/route/source ก่อนแก้
- อย่าเพิ่ม fast path/rule แบบสุ่มทุกครั้งโดยไม่คิดภาพรวม เพราะผู้ใช้ไม่อยากแก้ทีละเคสตลอดไป

## Daily Log

ต้องเขียน daily log เป็น `.md` เมื่อทำงานที่มีสาระ เช่น:

- แก้ logic
- เพิ่มข้อมูล
- เพิ่ม/แก้ test
- เพิ่ม eval
- เปลี่ยน routing/retrieval/LLM
- สร้าง handoff
- เปลี่ยน notebook หรือ local chat tool

Daily log อยู่ที่:

```text
C:\Users\Chokhun\Downloads\Learn-LLM\17_PSU_Esports_Daily_Logs
```

ชื่อไฟล์ใช้วันที่ เช่น `2026-07-23.md`

ไม่ต้องบอกผู้ใช้ทุกครั้งว่าเขียน daily log แล้ว เว้นแต่ผู้ใช้ถามหรือเป็น deliverable หลัก

## Testing Policy

- แก้ logic สำคัญต้อง compile/test เฉพาะจุด
- ห้ามแก้ test ให้ผ่านง่ายโดยไม่แก้สาเหตุจริง
- ถ้าเพิ่ม feature ใหม่ ควรเพิ่ม smoke/eval เฉพาะ feature นั้น
- ไม่ต้อง run eval ใหญ่ทุกครั้งถ้าไม่จำเป็น
- ถ้า user ขอ “ลองเช็คเอง” หรือ “ดูรายข้อ” ให้สร้าง JSON/CSV ที่อ่านง่ายและเก็บใน reports

## สิ่งที่ผู้ใช้ให้ความสำคัญ

- ความถูกต้องมากกว่าความเร็ว แต่ไม่ควรช้าเกินจำเป็น
- Local LLM ควรใช้ให้มีประโยชน์จริง ไม่ใช่เปิดไว้เฉย ๆ
- Typo/ภาษาวิบัติ/ทับศัพท์ต้องรองรับมากขึ้นเรื่อย ๆ
- คำถาม follow-up ต้องจำบริบทใน session ได้
- คำตอบต้องไม่ดึงข้อมูลผิดหมวด เช่น ถาม staff แล้วตอบเกม
- ต้องเห็น trace/mode/source_type ได้เวลา debug
