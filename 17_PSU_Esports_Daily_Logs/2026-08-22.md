# PSU Esports Daily Log - 2026-08-22

## Latest Update - Product Requirements, Capacity Review และ Model/Reranker Decision

### สรุปสิ่งที่ทำ

- สรุป Product target จากผู้ใช้: chatbot สาธารณะสำหรับเว็บไซต์และ Facebook, รันบน local server ตลอด 24 ชั่วโมง, เป้าหมายมากกว่า 100-200 คนต่อวัน, peak ประมาณ 20 sessions พร้อมกัน และต้องตอบกลับไม่เกิน 10 วินาที
- ตรวจผล benchmark เดิมเพื่อเปรียบเทียบ `scb10x/typhoon2.5-qwen3-4b` กับ `scb10x/llama3.2-typhoon2-3b-instruct`
- ตรวจสถานะ source ของข้อมูล game controls และผลทดลอง BGE reranker ที่มีอยู่จริง
- วิเคราะห์ข้อจำกัด capacity ของ LLM concurrency 1 เทียบกับ warm grounded composer ประมาณ 7.27 วินาที

### ปัญหาและ root cause

- ถ้า request พร้อมกัน 20 รายการเรียก LLM ทั้งหมด และ LLM ทำงานทีละ 1 รายการที่ประมาณ 7.27 วินาที รายการสุดท้ายอาจรอประมาณ 145 วินาที จึงไม่สามารถรักษา hard cap 10 วินาทีได้ด้วยการเรียก LLM ทุกคำถาม
- Full paired evaluation 1,600 เคสที่เปรียบเทียบ 4B/3B เป็นผลวันที่ 2026-07-31 และยังไม่ครอบคลุม latest latency changes
- ผล stratified 1,000 เคสวันที่ 2026-08-04 มี `llm_required_but_unavailable` 133 เคส จึงใช้ตัดสินคุณภาพ LLM โดยตรงไม่ได้
- Hardware ที่ผู้ใช้ระบุสำหรับ Product คือ i5-14400, RAM 32 GB และ RTX 5060 8 GB แต่ environment ที่ตรวจใน session นี้รายงาน RTX 4050 Laptop 6 GB จึงต้องยืนยันว่า benchmark เดิมและ Product จะรันบนเครื่องใด
- การเก็บ raw chat และข้อมูลระบุตัวบุคคลตลอดไปเพิ่มความเสี่ยงด้านความเป็นส่วนตัว การรั่วไหล และภาระการควบคุมข้อมูล

### สิ่งที่เพิ่มหรือแก้

- ยังไม่แก้ source code
- เสนอ policy สำหรับ Product: Fast/Structured/RAG deterministic เป็น fallback ที่ตอบได้เสมอ, synchronous LLM เป็น optional enhancement ตาม queue/deadline และใช้ shared LLM worker สำหรับทั้งเว็บและ Facebook
- เสนอให้ใช้ Typhoon 4B เป็น default ต่อไป และทดสอบ A/B ใหม่บนเครื่อง Product ก่อนพิจารณาเปลี่ยนโมเดล
- เสนอให้ BGE ปิดเป็นค่าเริ่มต้นใน MVP และเปิดเฉพาะกรณี candidate สูสีกันหลังพิสูจน์ accuracy/latency/memory บนเครื่อง Product

### เทคนิค/วิธีที่ใช้

- เปรียบเทียบ pass rate, average, P95, max และ LLM call count จาก benchmark เดียวกัน
- คำนวณ worst-case queue จาก `จำนวนงาน x เวลา LLM ต่อหนึ่งงาน` ภายใต้ concurrency 1
- ตรวจ metadata `coverage_status` ของ control JSON และตรวจรายงาน focused entity reranker/full eval
- แยก request ID, session ID และ user ID เพื่อออกแบบ trace, context และ identity คนละหน้าที่

### ผลทดสอบ/ผลวัด

- Full 1,600 วันที่ 2026-07-31: Typhoon 4B ผ่าน 94.75%, average 2.3089s, P95 12.5265s; Typhoon 3B ผ่าน 94.62%, average 2.3342s, P95 13.0106s; ทั้งคู่เรียก LLM 454 ครั้ง
- Pilot 34 เคส: 4B ผ่าน 91.18%; 3B ผ่าน 88.24%
- Latest No-LLM 1,600 หลัง boundary fix: ผ่าน 86.12%, average 0.45s, P95 0.92s, max 7.36s; คะแนนรวมต่ำจากกลุ่มที่ต้องใช้ general LLM จึงไม่ใช่ structured-only accuracy
- Focused BGE entity reranker 20 เคส: baseline accuracy 90%, reranker 95%; baseline average 0.061s, reranker average 0.5633s, reranker P95 0.8798s, model load 161.198s ในรอบนั้น
- Full 1,600 ของ cross-domain gate + gated BGE ให้ mode/route/answer/validation diff เท่ากับ 0 จาก baseline
- Control source: 38 ไฟล์ แบ่งเป็น `secondary_needs_manual_verify` 30 และ `partial_official` 8
- BGE cache บน disk ที่พบประมาณ 2.136 GB; ยังไม่มีค่าที่วัดตรงของ RAM/VRAM หลังโหลดบนเครื่อง Product

### ข้อจำกัดและงานที่ยังเหลือ

- ยังไม่ทราบ real traffic mix, จำนวนข้อความต่อ session, uptime target, retention policy และผู้รับผิดชอบ data approval/security อย่างเป็นทางการ
- ยังไม่มี shared queue, multi-user load test 20 sessions, session isolation test, Facebook webhook integration, monitoring/alerting, auto-restart และ recovery test
- ยังต้องตรวจ control mappings 30 เกมบนอุปกรณ์/การตั้งค่าจริงของ Studio
- ยังต้องกำหนด PDPA/privacy notice, data minimization, access control, encryption, retention และ deletion policy ก่อนเก็บ student ID หรือ raw chat ระยะยาว

### งานที่ควรทำต่อ

1. ยืนยันเครื่อง Product และรัน resource baseline ของ Typhoon 4B กับ BGE แยก RAM/VRAM/cold/warm
2. รัน full paired evaluation 1,600+ ล่าสุด แยก No-LLM และ Typhoon 4B แล้วจัด failure taxonomy
3. สร้าง multi-user load test 20 sessions พร้อม mixed traffic และ all-LLM stress เพื่อวัด queue wait, P95, max, timeout และ session leakage
4. กำหนด graceful-degradation policy และ shared LLM worker ก่อนเชื่อมเว็บ/Facebook
5. กำหนด data ownership, source approval/freshness และ privacy/retention policy ก่อน public pilot
