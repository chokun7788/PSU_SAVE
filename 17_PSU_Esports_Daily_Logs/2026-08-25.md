# PSU Esports Chatbot Daily Log - 2026-08-25

## Latest Update - Core Functions Architecture and Detailed Flows

### สรุปสิ่งที่ทำ

- จัดทำเอกสาร Target Architecture สำหรับ Core Functions 4 ส่วน ได้แก่ FAQ Chatbot, Check Slot, Input Data/Admin และ Booking/Payment
- แยกสถานะปัจจุบันออกจาก proposed design ชัดเจน เพื่อไม่ให้เข้าใจว่า Slot API, Admin UI, Booking transaction หรือ Payment verification มีใช้งานแล้ว
- กำหนดให้ WordPress เดิมเป็น Source of Truth ของ Slot/Booking และให้ Content Admin local เป็นแหล่งข้อมูลกลางของ FAQ/เกม/กฎ/อุปกรณ์

### ปัญหาและ Root Cause

- การเพิ่มข้อมูลปัจจุบันยังแก้ JSON/JSONL และรัน CLI ด้วยมือ ทำให้การเพิ่มข้อมูล exact กับ RAG ไม่เป็น workflow เดียวกัน และ runtime มี `lru_cache` หลายตำแหน่งที่ต้องจัดการตอน reload
- ยังไม่มี WordPress Booking API contract จึงยังไม่ทราบ plugin endpoint, resource ID, status mapping, atomic hold/TTL และ write semantics
- การอ่าน QR จากภาพสลิปเพียงอย่างเดียวพิสูจน์ไม่ได้ว่าเงินเข้าจริงและกันภาพที่ถูก crop/recompress ไม่ได้ ต้องใช้ Provider verification และ transaction reference
- PII และข้อมูลสลิปมีความเสี่ยงสูงกว่าประวัติ FAQ จึงไม่ควรเก็บรวมใน chat/trace log

### เทคนิคและวิธีที่ใช้

- Adapter pattern: แยก WordPress plugin และ Payment Provider ออกจาก domain contract ภายใน
- Canonical Record + Dual Projection: ข้อมูลอนุมัติหนึ่งชุดสร้างทั้ง Structured JSONL และ RAG chunks/index
- Human-in-the-loop publishing: LLM ช่วย extract Draft แต่ต้องผ่าน schema/source/freshness validation และ approver ก่อน Publish
- Atomic publish + active manifest: build/validate ทั้ง Structured และ RAG ก่อนสลับ version พร้อม rollback เมื่อ reload/smoke fail
- Interval arithmetic: รวม busy intervals แล้วลบออกจาก operating windows เพื่อคำนวณช่วงว่าง
- State machine + idempotency + outbox: คุม Booking/Payment, event ซ้ำ และกรณีรับเงินแล้ว WordPress sync ล้มเหลว
- Privacy boundary: แยก Secure Form และ booking/payment store ออกจาก Chatbot history/log

### ข้อจำกัดและงานที่ยังเหลือ

- เอกสารเป็น implementation contract ไม่ใช่ระบบที่เปิดใช้งานแล้ว
- ต้องได้ WordPress plugin/API/auth/resource/status/hold documentation ก่อนเชื่อม Slot และ Booking จริง
- ต้องกำหนด authoritative pricing, receiving account matching, Slip Provider, webhook endpoint, refund/reconciliation และ PII/slip retention policy
- SQLite เหมาะกับ local service และ admin write ต่ำ แต่ต้องพิจารณา PostgreSQL/shared queue เมื่อมีหลาย writer/process
- Slip verification ต้อง rollout แบบ observe/assist ก่อน auto-confirm เพื่อวัด false accept/false reject จากข้อมูลจริง

### งานที่ควรทำต่อ

1. ขอ WordPress Booking API contract และสร้าง canonical resource/status mapping
2. ทำ Mock Adapter + interval engine + Check Slot read-only page ก่อน เพราะยังไม่มี transaction risk
3. ทำ Content Admin แบบ draft/validate/approve และ migration inventory ของ JSONL เดิม
4. พัฒนา Booking state machine หลังยืนยันว่า WordPress รองรับ atomic hold/TTL
5. ทดสอบ Slip Provider แบบ shadow verification ก่อนเปิด auto-confirm
6. ทำ security, privacy, multi-user load และ recovery test ก่อน Production
