## ภาพรวมความเข้าใจของโปรเจกต์

โปรเจกต์นี้ไม่ใช่การ "เทรนโมเดลใหม่" ตั้งแต่ศูนย์ แต่เป็นการทำระบบตอบคำถามจากข้อมูลเฉพาะของ PSU Esports Studio - Phuket โดยใช้แนวทาง RAG เป็นหลัก

แนวคิดหลักคือให้โมเดลตอบจากเอกสารและข้อมูลที่เรามี ไม่ใช่ให้โมเดลจำทุกอย่างไว้ในน้ำหนักของโมเดล

สิ่งที่ต้องแยกให้ออกคือ:

- Model คือสมองภาษาที่ใช้เรียบเรียงคำตอบ
- Data คือความรู้จริงของศูนย์
- Embedding คือวิธีแปลงข้อความให้ค้นหาได้
- Vector Database คือที่เก็บข้อความแบบค้นหาด้วยความหมาย
- RAG คือกระบวนการดึงข้อมูลที่เกี่ยวข้องก่อนให้โมเดลตอบ
- Rule-based คือทางลัดสำหรับคำถามที่รู้แน่นอนและถามซ้ำบ่อย

## Timeline การทำงานของวัน

### ช่วงที่ 1 - ทำความเข้าใจ requirement

- อ่านความต้องการหลักของ chatbot
- แยกว่าผู้ใช้งานหลักคือคนทั่วไปหรือลูกค้าที่สงสัยเรื่องศูนย์
- สรุปว่า MVP ควรตอบ FAQ ให้ได้ก่อน
- ยังไม่ต้องทำ action เช่น จองจริง ยกเลิกจริง หรือเรียก API จริง
- จดไว้ว่า Facebook เป็นช่องทางสำคัญในอนาคต
- จดไว้ว่า Docker สำคัญ เพราะฝั่งมหาวิทยาลัยติดตั้งผ่าน Docker เป็นหลัก
- จดไว้ว่าต้องรองรับไทยและอังกฤษ
- จดไว้ว่าควรเน้น Local เพราะไม่ต้องการ API เสียเงิน

### ช่วงที่ 2 - ประเมินแนวทาง Local LLM

- พิจารณาว่าเครื่องศูนย์สามารถรันโมเดลขนาดเล็กถึงกลางได้
- สเปค CPU และ RAM เพียงพอสำหรับ RAG local
- GPU 8GB ช่วยให้ใช้โมเดล quantized ได้ดีขึ้น
- แนวทางที่เหมาะคือโมเดล 3B ถึง 4B ก่อน
- ไม่ควรเริ่มด้วยโมเดลใหญ่มาก เพราะ latency และ RAM/VRAM จะเป็นปัญหา
- สรุปว่า Qwen family เหมาะกับภาษาไทยและงานถามตอบมากพอสำหรับ MVP
- วางแผนให้ใช้ Ollama หรือ local runtime เพื่อโหลดและรันโมเดล

### ช่วงที่ 3 - วางโครงระบบ RAG

- กำหนดให้ data pipeline แยกเป็น raw, processed, curated
- Raw คือข้อมูลที่ scrape หรือดึงมาตรง ๆ
- Processed คือข้อมูลที่ทำความสะอาดแล้ว
- Curated คือข้อมูลที่มนุษย์จัดให้อ่านง่ายและเชื่อถือได้
- ตั้งแนวคิด chunking ว่าต้องไม่ตัดแค่ตามจำนวนคำ
- ควร chunk ตามหัวข้อ, intent, semantic unit, rule block, price table, และ FAQ unit
- ถ้าข้อมูลเป็นกฎ ควร chunk แยกตามข้อกฎ
- ถ้าข้อมูลเป็นราคา ควร chunk เป็นตารางค่าบริการหรือ service fee fact
- ถ้าข้อมูลเป็นตารางเวลา ควร chunk แยกวันและช่วงเวลา

### ช่วงที่ 4 - วางแผน Ground Truth

- เริ่มจากคำถามที่ผู้ใช้จริงน่าจะถาม
- แยกหมวดคำถามเป็นราคา, การจอง, กฎ, เกม, ข้อมูลศูนย์, ติดต่อ, ข่าว/กิจกรรม
- วางแนวคิดว่าคำถามต้องมีทั้งแบบตรงและแบบภาษาคนทั่วไป
- ตัวอย่างคำถามตรงคือ "เช็คอินล่วงหน้าได้กี่นาที"
- ตัวอย่างคำถามธรรมชาติคือ "ถ้าไปก่อนเวลาเยอะ ๆ เช็คอินได้ไหม"
- ตัวอย่างคำถาม typo คือ "เชคอินก่อนกี่นาที"
- ตัวอย่างคำถามผสมคือ "ถ้าจองแล้วไม่จ่าย แล้วไปเช็คอินช้าจะเกิดอะไร"
- Ground Truth ต้องมี expected keyword และ expected source เพื่อเช็คทั้งคำตอบและแหล่งอ้างอิง
