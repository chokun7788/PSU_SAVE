## Latest Update - Compound Complexity Gate and Bounded Parallel Execution

### เพิ่มอะไรไปบ้าง

- เพิ่ม `CompoundProfile` สำหรับจำแนกคำถามหลายส่วนเป็นงานอิสระหรือ complex/dependent ก่อนเข้า Planner และก่อนประมวลผล child
- เพิ่ม `CompoundNode` และ `CompoundPlan` เพื่อเก็บลำดับงานกับ dependency ของแต่ละส่วน
- เพิ่ม bounded parallel executor จำกัด worker สูงสุด 2 ตัวสำหรับ child ที่ผ่าน deterministic preflight เท่านั้น
- เพิ่ม ordered dependency chain สำหรับคำถามที่มีการอ้างอิงผลก่อนหน้า, การจัดอันดับ, การคำนวณ, การเปรียบเทียบ, คำถามกว้าง หรือผลจาก Planner
- ปิด LLM/RAG fallback ใน parallel child ที่ยืนยันแล้วว่าเป็น structured/fast route เพื่อลดการยิง Local LLM พร้อมกัน
- เพิ่ม `PSU_COMPOUND_MAX_WORKERS=2` ใน `start_local_ai_chat.ps1`
- เพิ่ม regression test `tests/smoke_test_compound_execution.py`
- เพิ่ม force gate ให้ complex compound เรียก constrained Query Planner ได้ แม้ deterministic splitter จะแยกส่วนได้แล้ว
- จำกัด Query Planner ของ complex compound ไว้ไม่เกิน 4 วินาที เพื่อกัน Planner timeout ลากทั้งคำถาม
- เมื่อ complex Planner timeout/invalid จะปิด child Intent LLM ชั่วคราว แล้วใช้ deterministic fallback ต่อทันที
- เพิ่ม dependency reference guard: ถ้าคำถามส่วนถัดไปอ้าง “เครื่องนั้น/โซนนั้น” และผลก่อนหน้ามีหลายคำตอบที่เสมอกัน ระบบจะถามเลือกแทนการเดา

### ใช้เทคนิค/วิธีไหน

- Complexity-aware routing: ใช้สัญญาณ dependency, reference, ranking/calculation, broad query และจำนวนส่วนในการจัดระดับ
- DAG/dependency planning: งานที่ไม่รู้ dependency จะถูกทำเป็น chain แบบ conservative เพื่อไม่เดาความสัมพันธ์ผิด
- Bounded parallelism: ขนานเฉพาะงานข้อมูลจริงที่ route category และ confidence ผ่าน preflight
- LLM budget protection: ไม่ให้ child ที่ขนานกันเรียก LLM พร้อมกัน และยังคง request deadline เดิม
- Constrained planner gate: เปิด Planner เฉพาะ complex case และใช้ schema/allowlist เดิมตรวจผล

## Latest Update - Paper Research for Complex Compound Latency

### วิเคราะห์อะไร

- ศึกษาปัญหา compound question ที่สะสมเวลาจาก planner, child pipeline, retrieval และ LLM หลายครั้ง
- เปรียบเทียบ Adaptive-RAG, LLMCompiler, EfficientRAG, Question Decomposition for RAG, FrugalGPT และ LLMLingua-2 กับ architecture ปัจจุบัน

### ข้อสรุปสำหรับโปรเจกต์

- เหมาะที่สุด: Complexity-Aware Router แบบ Adaptive-RAG เพื่อแบ่ง simple/medium/complex ก่อนเลือกวิธีประมวลผล
- เหมาะมาก: DAG Planner + bounded parallel executor ตามแนว LLMCompiler โดย parallel เฉพาะ structured/retrieval tasks และจำกัด Local LLM concurrency
- เหมาะมาก: ใช้ LLM เพียงครั้งเดียวต่อ complex workflow ตามแนว EfficientRAG; child steps ใช้ structured resolver/retrieval แทนการเรียก LLM ซ้ำ
- ใช้เฉพาะ complex multi-source: decomposition -> retrieval ต่อ sub-question -> merge -> rerank -> answer
- ใช้เป็นแนว policy: FrugalGPT cascade เพื่อหยุดเมื่อคำตอบจาก rule/structured เชื่อถือได้
- ยังไม่ใช่อันดับแรก: LLMLingua-2 เพราะ prompt ปัจจุบันไม่ยาวมาก; คุ้มเมื่อ RAG context ยาวจริง
- Hard timeout ด้วย worker/process ยังจำเป็น แต่เป็น systems control เสริม ไม่ใช่เทคนิคจาก paper โดยตรง
