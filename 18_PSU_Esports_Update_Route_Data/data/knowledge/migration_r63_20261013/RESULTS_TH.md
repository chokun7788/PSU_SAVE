# ผลการย้ายข้อมูลเดิมเข้า Format กลาง — R63 (13 ตุลาคม 2026)

## สถานะ

ย้ายเป็นร่างในฐานสำเนาจากโปรเจกต์จริงแล้ว ข้อมูลและการตอบเดิมยังทำงานด้วยฐานเดิม ไม่มีการอนุมัติหรือเผยแพร่แทนเจ้าของ ไม่มีการเปลี่ยนตาราง WordPress และไม่มีการเปลี่ยน ZIP R62 เดิม

- อ่าน canonical เดิม 270 รายการ และสำรองไฟล์ต้นฉบับ 280 ไฟล์ พร้อม SHA256
- ฐานสำเนามี 582 รายการ: เก็บร่างเดิม 41 รายการและทุก revision; สร้าง/เพิ่ม revision 543 ครั้ง โดยไม่มี approval/release ใหม่
- ตรวจช่องที่ย้าย 1933 ช่อง พร้อม source path, SHA256, JSON pointer และวิธีแปลง
- ไม่ใช้ log, Ground Truth, sample appointments หรือ fixture เป็นข้อเท็จจริงของศูนย์

## การเก็บข้อมูลเดิม

- `before.sqlite`: SQLite backup รวมข้อมูลใน WAL ก่อนการย้าย
- `original_files/`: สำเนา byte-for-byte ของทุกไฟล์ที่ใช้ รวม Excel ราคาเหมา
- `SOURCE_MANIFEST.json`: รายการไฟล์/ขนาด/hash
- `FIELD_LINEAGE.json`: ตารางการแปลงแต่ละช่อง
- `migration.bundle.json`: ร่างกลางพร้อม evidence snapshots (ยังไม่ใช่ release)
- `PENDING.json`: รายละเอียดช่องที่ยังแปลงไม่ได้/มีความต่าง/ไม่มีคำตอบ
- ข้อความตอบสั้นใน owner chat เก็บไว้ในต้นฉบับและหลักฐาน ส่วนฐานตอบเก็บคำตอบ TH/EN ที่เรียบเรียงไว้หนึ่งรายการต่อ claim เพื่อลดคำตอบซ้ำ ไม่ทับต้นฉบับ

## ผลตรวจอัตโนมัติ

1. ตรวจ schema + FK + evidence + การรักษา revision/ฐานเดิม + ขอบเขตเกม/เครื่อง/หัวข้อกติกา: **4922/4922 จุดตรวจ** ทั้งนี้จำนวนนี้เป็นการตรวจข้อมูล ไม่ใช่จำนวนคำถามที่ตอบถูก
2. คำถามไทยเดิมจากคำตอบที่ผู้ใช้ให้ 18 ข้อ + การอ่านวิธีเล่น/ข้อมูลอุปกรณ์ทั้งหมด 2 ข้อ: **20/20** ตรวจว่าเนื้อหาที่คาดต้องปรากฏจริง ใช้ draft preview และปิด LLM assist เฉพาะในการทดสอบนี้
3. เทียบ Excel ต้นฉบับกับราคา/ที่นั่ง/อุปกรณ์/หมายเหตุและ hash: **38/38** เก็บผล raw 37/38 ไว้ด้วย จุดต่างเดียวคือช่อง G7 มีช่องว่างท้ายคำ ยอมรับเฉพาะ trim ช่องว่างรอบนอก ไม่แก้ workbook
4. เรียก pipeline เดิมจริงกับคำถาม 20 ข้อ ไม่มี runtime error เก็บ answer/route/trace เทียบกับร่างใน `OLD_VS_DRAFT_BASELINE.jsonl`; ผลรอบนั้นชี้คำตอบซ้ำจากการย้ายทั้ง raw และ curated จึงแก้ให้เก็บ curated ต่อ claim เพียงรายการเดียวใน round7 คำตอบของระบบเดิมที่เก็บไว้ยังใช้เป็น baseline ได้เพราะฐานจริงไม่เปลี่ยน
5. ยังไม่รับรองคำถามทุกรูปแบบ หรือประสิทธิภาพเมื่อใช้งานหลายคน ไม่มีการทดลองจอง/เปลี่ยนข้อมูลลูกค้าจริง

## ข้อผิดพลาดที่พบและแก้ในตัวแปลง

1. ID เดิมที่มีจุดไม่ผ่าน schema ใหม่: แปลงเป็น underscore และแปลง FK ให้ตรงกัน เก็บ legacy ID/path ใน coverage และ lineage
2. reason ว่างถูกตีว่า known: คง unknown เมื่อต้นฉบับไม่มีข้อความ
3. เลขหัวข้อ RoV/VALORANT ซ้ำ ทำให้ข้อความบางหัวข้อหาย: ใช้ลำดับ occurrence เป็น ID และเก็บ section_index เดิมเป็น field ตอนนี้ครบทุก 104 หัวข้อ
4. alias ทำให้ Overcooked! และ Overcooked! 2 รวมกัน: ใช้ชื่อเกมต้นฉบับตั้ง identity; normalize เฉพาะ Unicode/ตัวพิมพ์/วรรคตอนและคงเลขภาคไว้ ไม่ใช้ alias กว้างกำหนด game_service
5. คำถาม FAQ เคยเป็น key เช่น player_identity: เปลี่ยนเป็นคำถามจริงจาก source_items พร้อมคงคำตอบไทย/อังกฤษเดิม
6. raw owner answer กับ curated owner answer ตอบซ้ำ: เก็บ raw ไว้ใน archive และใช้ curated record ที่ระบุ source_items เป็นรายการตอบหนึ่งรายการ

## ประเด็นที่ยังต้องแก้ก่อนเปิดใช้ฐานนี้แทนระบบเดิม

### งานทางเทคนิคที่ทำต่อได้โดยไม่ถามเจ้าของใหม่

- การถามอุปกรณ์ว่า “รายละเอียด” ยังอ่านเฉพาะ publish_core และไม่รวม usage ทั้งหมด; คำว่า “ข้อมูลทั้งหมด” อ่านครบในเคสทดสอบ ต้องปรับ read projection ให้เหมาะกับเจตนา
- ข้อความ “คนเล่นต้องเป็นคนที่จองหรือมีรายชื่ออยู่ในรายการจอง” ไม่ใช่ชื่อรายการและไม่เลือก FAQ ในการทดลองที่ไม่ใช้ LLM; ต้องตรวจ semantic selection ด้วย LLM/คำถาม paraphrase เพิ่ม การย้าย field ถูกไม่ได้รับรองว่าดึงถูก
- รายการเกมของศูนย์ต้องใช้ offered/service links กรองออกจากเกมที่มีแค่กติกา/คู่มือ
- facet/dependency ของกติกาและ gesture/context ของปุ่มต้องจับคู่กับรูปแบบเดิมให้ครบ หลายส่วนแก้ด้วยข้อมูลเดิมได้โดยไม่ต้องขอเจ้าของยืนยันนโยบายใหม่
- ต้องผูกรหัสเครื่อง/physical pool/occupancy กับ adapter จริง; VR 30 นาทีใช้ช่องเต็มชั่วโมงเป็นนโยบายที่ผู้ใช้เคยยืนยันแล้ว ไม่ต้องถามนโยบายนี้ซ้ำ
- ข้อความ FAQ ที่เป็นราคาหรือมี placeholder {service} ต้องแปลงไป typed scope ก่อนเผยแพร่ ไม่ใช้ FAQ เพื่อเลี่ยง validity ของ rate
- ต้องรวม/แยก duplicate facts ระหว่าง FAQ เก่า กฎเก่า และข้อมูลเฉพาะหมวดโดยใช้ provenance ก่อนเลือกเผยแพร่ ไม่เผยแพร่ทุก draft พร้อมกัน

### ข้อมูลที่ต้องถามเจ้าของเฉพาะเมื่อหลักฐานเดิมตอบไม่ได้

- ราคา Service Fee ที่พบระบุ 1 ก.พ.–31 มี.ค. 2026: หลัง 31 มี.ค. ใช้ฉบับใด และมีผลวันไหน? ย้ายช่วงเก่าเป็น interval ถึง 1 เม.ย. แบบ exclusive ไม่ยืดอายุให้เอง
- ราคาเหมา Excel ไม่มีวันเริ่ม/สิ้นสุด และครึ่งวัน/เต็มวันไม่มีจำนวนชั่วโมง: มีผลเมื่อไร และแต่ละช่วงได้กี่ชั่วโมง?
- เรตที่ระบุ 1–2 / 3–4 / 1–5 คนเป็นราคาต่อทั้งกลุ่มหรือมีฐานการคิดอื่น? ยืนยันเฉพาะ scope ที่ไม่มีหลักฐาน ห้ามอนุมานเป็นต่อคน
- นิยามเวลาเปิดพื้นที่ กับเวลาที่เปิดจองตรงกันหรือไม่? Dashboard มีช่วงต่อเนื่องรวมพักเที่ยง แต่ chat calendar แยก 09:00–12:00 / 13:00–16:00 คง conflicted แทนการเลือกฝั่งเดียว
- ขอบเขตแก้วันหลังจ่ายกับการเลื่อนแทนคืนเงินในข้อ 45/46 ดูต้นฉบับเต็มใน PENDING.json ไม่สรุปจากชื่อ key

## วิธีเปิดดูและแก้ร่าง

1. เปิด `Open-Migrated-Drafts.cmd` ในโฟลเดอร์ R63 หรือใน `data/knowledge/migration_r63_20261013` ของโปรเจกต์
2. เลือกหมวดแล้วเลือกรายการเดิม ช่องที่ known มีค่าที่คัดมาพร้อมหลักฐาน ช่อง unknown/conflicted มีหมายเหตุ
3. หากทดลองถาม ให้เลือกทดสอบร่าง (DRAFT PREVIEW) เพื่อให้เห็นข้อมูลที่ยังไม่เผยแพร่; หน้าเปิดจริงตั้ง LLM assist=1 ตามเดิม แต่ต้องมี local model พร้อม
4. บันทึกการแก้ไขสร้าง revision ใหม่ในฐานสำเนา ไม่ย้อนทับต้นฉบับ
5. รอบนี้ไม่อนุมัติ/เผยแพร่/สลับ normal chat มาฐานใหม่ การอนุมัติในหน้าร่างยังไม่ทำให้ normal chat เปลี่ยนฐาน ต้องผ่านการตรวจความครบ/การเลือกคำตอบและกระบวนการ activate อีกขั้น
6. ฐาน review มีข้อมูล legacy/V2 ด้วยจาก SQLite backup จึงรักษาข้อมูลเก่าที่เจ้าของเพิ่มไว้ ก่อนนำกลับต้องเทียบ revision ที่มีการแก้หลังวันที่สำรองเพื่อไม่ให้การแก้ระหว่างทางหาย

## สิ่งที่ไม่ได้ย้ายเป็นข้อเท็จจริง

ข้อมูลดัชนี vector, routing regex, no-answer/locale configuration, test fixtures, Ground Truth, chat logs และรายการจองสด ไม่เปลี่ยนให้เป็นความรู้ธุรกิจ ข้อมูล config ที่พบใน canonical เก็บต้นฉบับและเหตุผลใน COVERAGE.json
ข่าว/เหตุการณ์หรือช่อง schema ที่ต้นฉบับไม่มีข้อมูลจะไม่สร้างข้อมูลขึ้นเอง หมวด common schema มี 24 แบบ แต่งานนี้พบข้อมูลจริงที่ย้ายได้ 16 แบบ
