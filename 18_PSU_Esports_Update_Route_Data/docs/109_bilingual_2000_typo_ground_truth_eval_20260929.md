# ทดสอบคำถามพิมพ์ผิด 2,000 ข้อ (r15, 29 กันยายน 2026)

## ขอบเขตและวิธีทดสอบ

- สุ่มแบบกำหนด seed จาก `master_ground_truth_bilingual_10000_v2.jsonl` ภาษาไทย 1,000 ข้อและอังกฤษ 1,000 ข้อ โดยกระจาย 12 หัวข้อใกล้เคียงกัน
- สร้างคำถามพิมพ์ผิด 5 แบบอย่างละ 200 ข้อต่อภาษา: เบิ้ลตัวอักษร, กดแป้นข้างเคียง, ตัวอักษรหาย, สลับตำแหน่ง, และผสมแป้นข้างเคียงกับตัวอักษรหาย 2 จุด
- เก็บตัวเลข เวลา วันที่ รหัสเครื่อง และชื่อเป้าหมายที่ระบุชัดไว้ เพื่อลดการเปลี่ยนข้อเท็จจริงของคำถาม ตรวจแล้วทั้ง 2,000 ข้อมี ID ไม่ซ้ำ ข้อความเปลี่ยนจริง และ literal ที่ป้องกันยังอยู่
- รัน **คำถามต้นฉบับและคำถามพิมพ์ผิดเป็นคู่** ผ่าน `answer_question_pipeline_debug` รวม 4,000 ครั้ง โดยปิด LLM และ RAG fallback เพื่อวัดเส้นทางที่ทำซ้ำได้ ใช้ route, สถานะคำตอบ, ข้อความที่ต้องมี/ห้ามมี และเวลา ตามเกณฑ์ของ master GT
- ตรวจตัวอย่าง 6 คู่ (12 คำขอ) เพิ่มผ่าน API ของแพ็กเกจ r15 ที่เปิดอยู่บน `127.0.0.1:8095` ซึ่งเปิดตัวช่วยโมเดลจริง การตรวจนี้เป็นเพียง spot check ไม่ใช่ผลทั้ง 2,000 ข้อของหน้าเว็บ

## จุดเสียหลักที่พบ

1. **คำบอกเจตนาหรือคำเชื่อมเสีย ทำให้เลือกงานผิด** — ไทย: `PUBG: BATTLEGROUNDS ราคาเท่าไหร่` → `ราคเท่าไฟร่` เปลี่ยนจากตอบราคาเป็นรายละเอียดเกม; `PS5 ราคาเท่าไหร่ แล้วมีเกมอะไรบ้าง` → `เกมะไรบ้าง` เหลือคำตอบเฉพาะราคา ไม่ตอบส่วนรายชื่อเกม อังกฤษ: `temporary suspension` → `teporary suspension` จากคำตอบกฎระงับสิทธิ์เป็นไม่พบข้อมูล ตัวอย่างเหล่านี้ตรวจซ้ำบน API แล้วเกิดแบบเดียวกัน
2. **ยังเลือกหมวดเดิมได้ แต่ดึงคำตอบเฉพาะเรื่องไม่ครบ** — อังกฤษ `What does the Tab button do in VALORANT on PC` → `buttno` ยังคงอยู่หมวดเกม แต่เปลี่ยนจากคำตอบปุ่ม Tab ไปเป็นข้อความว่าไม่มีคำแปลอังกฤษที่อนุมัติแล้ว ไทยบางข้อยังอยู่หมวดเกมแต่ตอบไม่พบข้อมูลเมื่อคำถามย่อย เช่น `มี...ไหม` ถูกพิมพ์ผิด
3. **คำถามสถานะจองไวต่อคำว่า “ว่าง”** — `ช่วง 14:00-15:00 Cockpit Zone เครื่องไหนว่างบ้าง` → `ว่าบง้าง` เปลี่ยนจากเส้นทางตรวจสถานะเวลาเป็นหมวดเกมใน API ที่เปิดอยู่ **แม้คำถามเดิมก็ยังยืนยันสถานะสดไม่ได้** เพราะ Dashboard ไม่พร้อมในตอนตรวจ จึงพิสูจน์ได้เพียงว่า route เสีย ไม่ได้พิสูจน์ว่าเครื่องว่างหรือถูกจองจริง
4. **คำอังกฤษที่พิมพ์ผิดแล้วกลายเป็นคำจริงอีกคำ** — `How do you play Moving Out 2` → `How do you pay Moving Out 2` ทำให้ระบบไปตอบค่าบริการได้ การเปลี่ยนนี้กำกวมทางความหมาย จึงไม่ควรบังคับแก้ `pay` กลับเป็น `play` อัตโนมัติ และไม่ควรนับเป็นความผิดของระบบโดยไม่มีคนตัดสินเจตนา
5. **ปัญหาที่มีอยู่ก่อนพิมพ์ผิด** — กติกาแข่งขันภาษาอังกฤษ 72/84 ข้อต้นฉบับคาด `answer_available` แต่ระบบตอบ `localization_pending` เพราะยังไม่มีคำแปลที่อนุมัติแล้ว นี่คือความไม่ตรงกันของ GT กับสถานะเนื้อหาอังกฤษ ไม่ใช่ผลของ typo ห้ามเปลี่ยนเป็นคำตอบอังกฤษที่ยังไม่อนุมัติเพื่อเพิ่มคะแนน

หัวข้อที่ regression สูงสุด: ไทย `service_fee` 14, `studio_rules_penalties` 13, `members_overview_contact` 12; อังกฤษ `compound_context_boundary` 27, `game_controls` 25, `reservation_policy` 15 จากประมาณ 83–84 ข้อต่อหัวข้อ/ภาษา ตัวเลขข้อผิดพลาดของ route/status/content ซ้อนกันได้ จึงไม่ควรนำมาบวกกัน

## สิ่งที่ตรวจผ่าน และสิ่งที่ยังยืนยันไม่ได้

- สคริปต์สร้างชุดทดสอบและวิเคราะห์ผ่านการตรวจไวยากรณ์ Python ชุดข้อมูลครบ 2,000 แถว ไม่มี ID ซ้ำ อัตราส่วนภาษา/ชนิด typo ตรงตามแผน
- การรัน 4,000 ครั้งเสร็จครบ ไม่มี pipeline exception; API spot check ทั้ง 12 คำขอได้ HTTP 200 แต่ HTTP 200 ไม่ได้แปลว่าคำตอบถูก
- พบ 1 ข้อไทยที่ direct pipeline ใช้ **119.188 วินาที** เกินเพดาน 20 วินาที เมื่อรันซ้ำข้อเดียวใช้ **8.622 วินาที** และยังตอบไม่ผ่านเพราะ typo ข้อมูลรอบนี้ยังไม่พอชี้ว่าความช้าเกิดจากอะไรหรือเกิดซ้ำสม่ำเสมอ
- ป้ายกำกับของ 2,000 ข้อมี `generated_paraphrase_pending_review` 1,021, `source_grounded_gold_candidate` 373, และ `inherited_gold_candidate` 606; **ไม่มีสถานะยืนยันโดยเจ้าของครบทั้งชุด** คะแนนจึงเป็นผลเทียบเกณฑ์ภายใน ไม่ใช่ความแม่นยำที่รับรองโดยคน
- GT ของ `live_booking` วัดหลัก ๆ ว่าไปเส้นทาง lookup ถูกหรือไม่ ไม่มี fixture สถานะว่าง/ถูกจองจริงของเวลาที่ทดสอบ ไม่อาจสรุปความถูกต้องของคำตอบสถานะเครื่อง
- การสุ่มตำแหน่ง typo อาจโดนคำเกริ่นนำที่ไม่สำคัญ ทำให้คะแนนดูดีกว่ากรณีผู้ใช้พิมพ์ผิดในคำสำคัญ และบาง edit สร้างคำจริงที่เปลี่ยนความหมายดังตัวอย่าง `play`/`pay`
- 2,000 ข้อหลักปิด LLM ต่างจากแพ็กเกจใช้งานจริงซึ่งเปิด LLM; API spot check ให้หลักฐานว่าความเสียหายตัวอย่างยังเกิดจริง แต่ไม่พอแทนการวัดทั้งชุดบนหน้าเว็บ

## ลำดับแก้ไขที่มีหลักฐานรองรับ

1. ให้ตัวแก้คำผิดเสนอตัวเลือกสำหรับ **คำบอกเจตนาและคำเชื่อมภายในประโยค** ก่อนเลือก route/แยกคำถาม เช่น ราคา, ว่าง, ระงับสิทธิ์, button, policy, availability โดยรักษาชื่อเกม/เครื่อง/วัน/เวลาไว้ เปรียบเทียบคำตอบจากข้อความเดิมกับข้อความที่ซ่อม แล้วใช้ตัวเลือกที่มั่นใจสูงเท่านั้น
2. เพิ่มตัวตรวจความกำกวมเมื่อ typo อาจกลายเป็นคำจริงอีกคำ (`play`/`pay`) หรือการซ่อมทำให้คำถามเปลี่ยนหัวข้อ ควรถามยืนยันสั้น ๆ แทนการเดา
3. หลังแก้ข้อ 1–2 ให้รัน **239 regression IDs** ก่อน แล้วรันชุด 2,000 ข้อเดิมอีกครั้งพร้อม clean baseline เพื่อวัดผลและ regression ใหม่ แยกข้อที่ยังไม่มีคำแปลอนุมัติออกจากคะแนน typo
4. ประสานเจ้าของข้อมูลเฉพาะเรื่องคำแปลกติกาแข่งขันอังกฤษ: ต้องการให้ GT คาด `localization_pending` จนกว่าจะอนุมัติคำแปล หรือจะให้เจ้าของตรวจและอนุมัติคำแปลก่อน จึงค่อยเปลี่ยน expected answer เป็น `answer_available`
