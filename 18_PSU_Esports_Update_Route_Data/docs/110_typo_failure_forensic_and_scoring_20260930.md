# วิเคราะห์สาเหตุและวิธีให้คะแนนของข้อทดสอบพิมพ์ผิด 2,000 ข้อ

วันที่ 30 กันยายน 2026 · ระบบ r15 · วิเคราะห์ต่อจาก `docs/109_bilingual_2000_typo_ground_truth_eval_20260929.md`

## ข้อสรุปที่ต้องอ่านก่อนตัวเลข

ผล 2,000 ข้อเป็นการเทียบคำถามเดิมกับคำถามที่เพิ่ม typo อย่างละ 1,000 ข้อต่อภาษา โดยปิด LLM และ RAG fallback ในการรันหลัก จาก 239 ข้อที่ **เดิมผ่านเกณฑ์ แต่ typo แล้วไม่ผ่าน** แบ่งตามจุดแรกที่เกณฑ์ตรวจพบเป็น: route 154, สถานะคำตอบ 54, เนื้อหา 31 ข้อ ตัวเลขนี้เป็น **การจัดกลุ่มเชิงกลไก** ไม่ใช่จำนวนคำตอบผิดที่เจ้าของศูนย์รับรองแล้ว

| จุดแรกที่ไม่ผ่าน | ไทย | อังกฤษ | รวม | ความหมาย |
|---|---:|---:|---:|---|
| route | 71 | 83 | 154 | เลือกหมวดนอกกลุ่มที่ GT ยอมรับ แม้บางคำตอบยังปฏิเสธอย่างปลอดภัย |
| status | 16 | 38 | 54 | หมวดยังยอมรับได้ แต่ควรตอบ/ขอความชัดเจน/ไม่ตอบ/lookup ต่างจากเกณฑ์ |
| content | 14 | 17 | 31 | หมวดและสถานะผ่าน แต่ข้อความไม่ผ่านสัญญา `must_contain`/`must_contain_any` |

แบบพิมพ์ผิด 2 จุด (`mixed`) ทำให้เกิด regression 82/400 ข้อ มากกว่าเบิ้ล 26/400 ข้อ ภาษาอังกฤษพลาดมากกว่าไทยใน *ชุดนี้* (138 ต่อ 101) เพราะชุดข้อมูลและเส้นทางตอบต่างกัน ห้ามสรุปว่าภาษาอังกฤษโดยทั่วไปสะกดยากกว่าหรือระบบไทยดีแล้ว

## ระบบเลือกคำตอบอย่างไร และตัวเลข “confidence” หมายถึงอะไร

เส้นทางสำคัญคือ **ข้อความ → แยกคำถามหลายเรื่อง → preprocess/แก้ typo แบบจำกัด → ดึง entity → ตัวตอบเฉพาะที่มีสิทธิ์ก่อน → router ตามลำดับกฎ → ดึงข้อมูล/สร้างคำตอบ → ตรวจความปลอดภัย → แสดงผล** (`app/pipeline/engine.py`, `preprocess.py`, `router.py`). จุดที่ต้องแยกกันมีดังนี้

1. **ตัวตรวจข้อความแปลกไม่ใช่ตัวสะกดคำ**: `app/pipeline/input_recovery.py` ให้คะแนนความผิดปกติจาก character n-gram แล้วเพียงเสนอให้ทบทวน intent เมื่อข้อความยาวไม่เกิน 48 ตัวและคะแนนถึงเกณฑ์ปกติ 0.43 ไม่ได้แก้ข้อความเอง ใน API ตัวอย่าง `ว่าบง้าง` ได้ 0.3112, `teporary` ได้ 0.2794, `buttno` ได้ 0.4079 จึงไม่มีตัวใดเปิดการทบทวนด้วยสัญญาณนี้
2. **ตัวซ่อมคำที่มีอยู่ระวังการแก้เกิน**: `keyboard_neighbor_recovery.py` รับเพียงคำไทยเป้าหมาย `สวัสดี`, `จอง`, `ว่าง`, `เกม` ในบริบทสั้นและแทนแป้นข้างเคียงเพียงหนึ่งจุด; `thai_transposition_recovery.py` รับกรอบ “...ได้บ้าง” แคบ ๆ; `multi_error_phrase_recovery.py` รับคำถามสำเร็จรูปบางชุดและปฏิเสธข้อความมีเวลา/วันที่/URL จึงไม่ซ่อม `ราคเท่าไฟร่`, `เครื่องไหนว่าบง้าง`, `teporary`, `buttno` หรือประโยคหลายเรื่องที่เสียส่วนหนึ่ง
3. **การแยกคำถามเกิดก่อน preprocess**: `_split_multi_question()` ถูกเรียกตั้งแต่ต้นใน `engine.py` ถ้าคำว่า `มีเกมอะไรบ้าง` เสียเป็น `มีเกมะไรบ้าง` ส่วนที่สองอาจไม่ผ่านตัวแยก แม้ราคาส่วนแรกยังชัด จึงตอบเพียงราคา
4. **route ส่วนใหญ่เป็นกฎตามลำดับ**: `router.py` ใช้ `if/elif` และข้อความที่ตรงกฎก่อนจะชนะ คะแนนเช่น 0.97, 0.95, 0.88 ส่วนใหญ่เป็นค่าคงที่ของสาขา ไม่ใช่ความน่าจะเป็นว่าเข้าใจเจตนาถูก 97% มีตัวเทียบ character n-gram ใน `semantic_intent.py` แต่ตัวอย่างที่เจาะ 14 คำถามไม่ผ่านเกณฑ์ semantic intent เลย
5. **คำตอบอาจมีคะแนนสูงเพราะแหล่งข้อมูลของ “หัวข้อที่เลือกผิด” มีจริง**: typo ราคา PUBG ไปเข้าหมวดเกม แล้ว renderer คืนเรื่องย่อเกมด้วย confidence 0.94; `buttno` ยังคงจับชื่อ VALORANT ได้ จึงคืนคำเตือน localization pending ที่ confidence 0.99 ความมั่นใจนี้ไม่ได้วัดว่าตอบคำถามเรื่องราคา/ปุ่มตรงประเด็น
6. **LLM ไม่ได้แก้ทุกเส้นทาง**: API จริงเปิดตัวช่วยโมเดล แต่คำถามที่ deterministic handler ตัดสินก่อนจะไม่เรียกโมเดล ใน `teporary suspension` มีการทบทวน intent ผ่านโมเดลจริง ทว่าเลือก candidate `general/unknown` และลงท้าย `english_no_answer` บันทึก trace ไม่รองรับการอ้างว่า “พิมพ์ผิดแล้วโมเดลจะช่วยได้เสมอ”

คะแนน **benchmark** คนละอย่างกับ confidence ของระบบ: `tools/run_master_ground_truth_eval.py` ให้ผ่านต่อเมื่อ route อยู่ในรายการที่ยอมรับ, status ตรงตามเกณฑ์, contract ข้อความผ่าน, และ latency ไม่เกินเพดาน ถ้าข้อใดไม่ผ่านคือ fail โดยไม่มีคะแนนบางส่วน (`tools/run_bilingual_2000_typo_eval_20260929.py`)

## เจาะเหตุและคำตอบที่ควรได้

### A. ราคาของ PUBG: คำบอกราคาหาย แล้วข้อมูลเกมที่ถูกต้องกลายเป็นคำตอบผิดเรื่อง

`MASTER-GT-TH-00085`: `PUBG: BATTLEGROUNDS ราคาเท่าไหร่` → `PUBG: BATTLEGROUNDS ราคเท่าไฟร่`

- **ก่อน typo**: entity `price_intent=True`; route `service_fee` 0.95; คำตอบ `structured_service_fee_by_game` อธิบายว่าไม่มีราคาตามชื่อเกม ต้องดูค่าบริการของโซน/กลุ่มผู้ใช้
- **หลัง typo**: `price_intent=False` เพราะคำหลักไม่ตรง; ชื่อ PUBG ยังชัด; router ลง `games_lookup` 0.88 แล้วตัวตอบเกมส่งเรื่องย่อ PUBG ด้วย confidence 0.94
- **เกณฑ์ให้ fail เพราะอะไร**: route เปลี่ยน `service_fee` → `games` แม้ contract เนื้อหา `must_contain: PUBG` จะผ่านทั้งคู่ จึงเห็นช่องโหว่: ถ้าไม่ได้ตรวจ route ก็อาจให้คำตอบผิดเรื่องผ่าน
- **คำตอบที่ควรได้**: อธิบายว่าเกมไม่มีราคาเฉพาะชื่อเกม ให้ตอบค่าบริการ PC Zone ตามกลุ่มผู้ใช้จากตารางค่าบริการที่ *ตรวจว่าเป็นฉบับล่าสุดแล้ว* หรือถามกลุ่มผู้ใช้เพื่อให้ราคาที่เกี่ยวข้อง หน้าเว็บจองทางการระบุ PUBG อยู่ในรายชื่อเกมของ PC และมีตารางค่าบริการแยกต่างหาก: [เว็บไซต์จองของศูนย์](https://esports.computing.psu.ac.th/)

**ความเสี่ยงข้อมูลเพิ่มเติม**: `app/calculator/service_fee.py` ยังอ้างรูปค่าบริการใน URL เดือน **มกราคม 2026** แต่หน้าเว็บไซต์จองทางการขณะตรวจฝัง[รูปค่าบริการใน URL เดือนสิงหาคม 2026](https://esports.computing.psu.ac.th/wp-content/uploads/2026/08/PSU-Esports-Studio-phuket-SERVICE-FEE.png) ยังไม่ได้เทียบตัวเลขในรูป จึงไม่ยืนยันว่าราคา 0/25/70 หรือราคาอื่นในคำตอบเดิมเป็นราคาปัจจุบัน และไม่แก้ตารางราคาโดยเดา

### B. ถาม Cockpit ว่างตามเวลา: คำว่า “ว่าง” เสีย แล้วถูกตีเป็นคำถามเกม

`MASTER-GT-TH-00890`: `ช่วง 14:00-15:00 Cockpit Zone เครื่องไหนว่างบ้าง` → `...เครื่องไหนว่าบง้าง`

- **ก่อน typo**: ตัวตรวจ live status เห็นคำว่า `ว่าง` พร้อมเวลาและ Cockpit จึงเข้าทาง `schedule/live_booking_status`; ในรอบ API ที่ตรวจ Dashboard ไม่พร้อม ระบบตอบว่า **ยืนยันสถานะสดไม่ได้** ไม่บอกว่าเครื่องว่างหรือถูกจอง
- **หลัง typo**: ตัวตรวจ `app/booking/live_status.py` ต้องพบสัญญาณเช่น `ว่าง`, `ถูกจอง`, `available`; `ว่าบง้าง` ไม่ตรง จึงข้าม live handler ส่วนกฎเกมเห็น `เครื่องไหน` กับคำอังกฤษที่ดูเหมือนชื่อเป้าหมาย จึงลง `games/game_availability_lookup` 0.95 สุดท้ายถามให้ระบุชื่อเกม ทั้งที่ผู้ใช้ระบุโซนแล้ว
- **เกณฑ์ให้ fail เพราะอะไร**: คาด route `schedule`/`reservation` และ mode ของ live lookup; กลับได้ `games`/`game_target_ambiguous` 0.95 ตัววัด status ยังตีคำตอบ “กรุณาระบุชื่อเกม” เป็น `answer` เพราะ heuristic ไม่รู้จักโหมดนี้ว่าเป็น clarification
- **คำตอบที่ควรได้**: ถ้า Dashboard ยังใช้ไม่ได้ ให้แจ้งว่า **ยังตรวจไม่ได้ว่า Cockpit #1/#2 ว่างตลอด 14:00–15:00 หรือไม่** พร้อมทางตรวจหน้าจอง ถ้า Dashboard พร้อมจึงดึงสถานะของทั้งสองรายการและตอบว่าง/ไม่ว่างตามข้อมูลสด ห้ามอนุมานจากตารางเวลาเปิด

### C. PS5 ถามสองเรื่อง: ส่วนรายชื่อเกมหายจากคำตอบ

`MASTER-GT-TH-04867`: `PS5 ราคาเท่าไหร่ แล้วมีเกมอะไรบ้าง` → `PS5 ราคาเท่าไหร่ แล้วมีเกมะไรบ้าง`

- **ก่อน typo**: splitter แยกเป็น 2 งาน route สุดท้าย `multi_question` 0.92 ตอบราคา PS5 และรายชื่อเกม
- **หลัง typo**: การแยกก่อน preprocess เห็นส่วน `มีเกมะไรบ้าง` ที่ไม่ตรงรูปแบบ จึงเหลือ 1 งาน; `price_intent=True` และ PS5 ยังชัด จึงตอบเฉพาะค่าบริการผ่าน `service_fee` 0.97
- **เกณฑ์ให้ fail เพราะอะไร**: route ต้องเป็น `multi_question` แต่ได้ `service_fee` สัญญา `must_contain_any: [PS5, บาท, เกม]` ใช้ **OR** ไม่ใช่ AND ดังนั้นคำตอบราคาอย่างเดียวผ่าน content check เพราะมีคำว่า “บาท” ทั้งที่ขาดครึ่งหนึ่งของคำถาม
- **คำตอบที่ควรได้**: สองส่วนแยกหัวข้อ: ราคาตามกลุ่มผู้ใช้จากตารางล่าสุดที่ยืนยันแล้ว **และ** รายชื่อเกม PlayStation 5 ที่ยืนยันได้จากรายการศูนย์ ไม่ใช่ตอบราคาเพียงอย่างเดียว

### D. กฎระงับสิทธิ์: exact phrase หลุด แล้วโมเดลช่วยไม่สำเร็จ

`MASTER-GT-EN-03895`: `temporary suspension` → `teporary suspension`

- **ก่อน typo**: protected intent เจอวลีตรงตัว ตอบกฎชั่วคราว 1–7 วันด้วย route `penalty` confidence 0.98
- **หลัง typo**: protected intent ไม่ทำงาน, router เริ่ม `general/unknown_domain_query` 0.55; API จริงเปิด LLM และ trace ระบุว่าลองทบทวน intent แต่เลือก `general/unknown` ก่อนจบที่ `english_no_answer` confidence 0.52
- **เกณฑ์ให้ fail เพราะอะไร**: คาด `penalty` กับคำตอบที่มีข้อมูล; ได้ `no_answer`
- **คำตอบที่ควรได้**: กรณีละเมิดซ้ำหรือรุนแรง **อาจ**ถูกระงับสิทธิ์ชั่วคราว 1–7 วันตามลักษณะเหตุ เจ้าหน้าที่แจ้งก่อน ตาม [กฎบนเว็บไซต์จองทางการ](https://esports.computing.psu.ac.th/) ไม่ควรตอบว่าทุกกรณีถูกระงับแน่นอน

### E. ปุ่ม Tab ใน VALORANT: ชื่อเกมอยู่ แต่ชนิดคำถามหาย

`MASTER-GT-EN-02806`: `What does the Tab button do in VALORANT on PC` → `...Tab buttno do...`

- **ก่อน typo**: `button` ตรงกฎ `game_control_lookup` 0.97; English renderer คืนรายการปุ่ม และ `Tab: Show Scoreboard` ด้วย confidence 0.96
- **หลัง typo**: กฎ control ไม่เห็น `button`; แต่ target lock ยังรู้จัก VALORANT จึงเข้า game detail ซึ่งยังไม่มี English localization ที่อนุมัติ แล้วตอบ `missing_english_localization` confidence 0.99
- **เกณฑ์ให้ fail เพราะอะไร**: route กว้าง `games` ยังถูก แต่ status กลายเป็น `localization_pending` และข้อความไม่มี `Tab` หรือ `Show Scoreboard`
- **คำตอบที่ควรได้**: ตาม **รายการปุ่มจากแหล่งรองที่เก็บในโปรเจกต์** Tab แสดง scoreboard แต่ไฟล์ `data/control_game_split/pc/valorant.jsonl` ระบุ `secondary_needs_manual_verify` จึงต้องบอกว่าการตั้งค่าบน PC ของศูนย์ **ยังไม่ได้ตรวจยืนยัน** ไม่ควรยืนยันว่าเครื่องจริงกดแล้วได้ผลนี้แน่นอน

### F. `play` → `pay`: typo ที่กลายเป็นคำจริงอีกความหมาย

`MASTER-GT-EN-02255`: `How do you play Moving Out 2` → `How do you pay Moving Out 2`

- ชื่อเกมยังตรง แต่คำหลักเปลี่ยนจากวิธีเล่นเป็นการจ่ายเงิน ระบบจึงตอบค่าบริการ Nintendo Switch จากข้อมูลราคาที่มี GT เดิมคาดหมวดเกม/สถานะ translation pending จึงนับ regression
- **คำตอบ “จริง” ไม่มีคำเดียว** หากเห็นเพียงประโยค `pay` เพราะผู้ใช้อาจหมายถึงราคาอยู่แล้ว ควรถามสั้น ๆ ว่าต้องการ **วิธีเล่น Moving Out 2** หรือ **ค่าบริการโซนที่มีเกมนี้** การฝืนแก้ `pay` กลับ `play` อัตโนมัติอาจทำให้ความหมายของผู้ใช้ผิด
- เว็บไซต์ศูนย์มี Moving Out 2 ใน [รายการเกม Nintendo Switch](https://esports.phuket.psu.ac.th/Services/our-games) แต่หน้าเว็บนี้ไม่ได้ยืนยันเจตนาของผู้ถามรายนี้

### G. กติกาแข่งขันอังกฤษ: ผิดตั้งแต่ข้อความต้นฉบับ ไม่ใช่ typo

ในกลุ่ม `competition_rules` อังกฤษ 72/84 ข้อต้นฉบับคาด `answer_available` แต่ระบบตอบ `localization_pending` เพราะเนื้อหาอังกฤษยังไม่ผ่านกระบวนการอนุมัติ ตัวอย่าง `MASTER-GT-EN-04469` route ถูกทั้งก่อนและหลัง typo และคำตอบเหมือนเดิม แต่ fail เพราะ expected status ไม่ตรง ส่วนนี้ต้องทบทวน GT หรืออนุมัติคำแปลจากหลักฐานก่อน **ห้ามสร้างกติกาอังกฤษโดยคาดเดาเพื่อเพิ่มคะแนน**

### H. ตัวตรวจให้ fail ทั้งที่ยังปฏิเสธอย่างปลอดภัย

`MASTER-GT-TH-04758` ถามเรื่องส่งเครื่องเกมไปบ้าน: ประโยคเดิม route `no_answer`, หลัง typo route `games` แต่ทั้งคู่บอกว่าไม่พบข้อมูลที่ยืนยันได้ เกณฑ์ให้ fail เพราะ route ต่างกัน ข้อนี้เป็น **route defect** แต่ยังไม่มีหลักฐานว่าแชทบอทอนุญาตให้นำเครื่องกลับบ้านผิด ๆ

อีกด้านหนึ่ง `MASTER-GT-TH-04858` ถาม Roblox ได้คำตอบว่า **ไม่พบ Roblox ในรายการเกมที่ยืนยันได้** แต่ตัววัด status ตีเป็น `answer` เพราะจับคำว่า “ไม่พบข้อมูล” หรือ mode บางชนิด ไม่ได้ตีความ “ไม่พบ Roblox” จึง fail ทั้งที่คำตอบส่วนหลักปลอดภัย ตัวอย่างนี้แสดงว่าคะแนนต่ำกว่าคุณภาพจริงได้

## จุดที่การให้คะแนนยังบิดเบือนภาพ

1. **ไม่มี positive content contract 1,107/2,000 ข้อ**; ใน 239 regression มี 120 ข้อในกลุ่มนี้ จึงตรวจได้แค่ route/status/latency หรือข้อความที่ห้าม ไม่ได้พิสูจน์ว่าตอบสาระครบ
2. **`must_contain_any` เป็น OR**: `PS5/บาท/เกม` ผ่านด้วยคำใดคำหนึ่ง การแยกสองคำถามหรือความสัมพันธ์ `Tab → scoreboard` ยังไม่ได้ถูกวัดเป็นสัญญาแบบคู่
3. **status เป็น heuristic จาก mode/วลีในคำตอบ**: `game_target_ambiguous` 3 ข้อถูกติดป้าย `answer`; “ไม่พบ Roblox” ถูกติดป้าย `answer` ทั้งที่เป็นการไม่ยืนยันเกม จึงเกิดทั้ง false alarm และการจัดประเภทผิด
4. **`live_lookup_required` วัดการเข้าทาง live เท่านั้น**: ดูว่าชื่อ mode มี `live`, `booking`, `schedule`, `calendar`, `opening`; ไม่ได้ตรวจว่าเครื่องว่างหรือถูกจองจริง ใน 166 ข้อ `live_booking` มีถึง 157 ข้อที่ไม่มี positive content contract
5. **คำถามต้นฉบับเองไม่ผ่าน 210/2,000 ข้อ**: 72 ข้อเป็นกติกาแข่งขันอังกฤษที่ localization pending; ไทยกลุ่ม `compound_context_boundary` มี 40 clean failures หลายข้อเป็นคำถามทั่วไปที่ benchmark ปิด LLM จึงได้ no-answer หรือ GT contract กำหนดถ้อยคำขัดกับ no-answer ห้ามนับทั้งหมดเป็นผลจาก typo
6. **synthetic edit อาจเปลี่ยนเจตนาจริง** (`play` → `pay`) และอาจตกในคำเกริ่นที่ไม่มีผล จึงไม่ใช่ตัวแทนความถี่/ความยากของข้อความลูกค้าจริง ผู้ติดป้ายทุกข้อยังเป็น `candidate` หรือ pending review: generated paraphrase 1,021; source-grounded candidate 373; inherited candidate 606
7. **latency outlier 1 ข้อ**: `MASTER-GT-TH-03901` ใช้ 119.188 วินาทีในการรันแรก แม้เพดานตั้ง 20 วินาที รันซ้ำใช้ 8.622 วินาทีและยัง fail ด้านคำตอบ ไม่มีหลักฐานพอชี้สาเหตุความช้า ต้องเก็บ trace/timing เพิ่มถ้าเกิดซ้ำ และทดสอบ timeout ของ API แยกจาก direct function

## อะไรยืนยันได้ และอะไรยังไม่ยืนยัน

**ยืนยันจากการรันอัตโนมัติและ trace**: ตัวเลขกลุ่ม fail, ข้อความหลัง preprocess ที่ไม่ถูกซ่อม, ค่า entity, route/intent/mode/confidence, ลำดับ stage, และ API spot check ที่ได้ HTTP 200 พร้อมคำตอบผิดเรื่องตามตัวอย่าง A–E

**ยืนยันจากแหล่งทางการ**: กฎระงับสิทธิ์ 1–7 วัน, รายชื่อเกม Moving Out 2/PUBG ตามหน้าเว็บไซต์ศูนย์, และหน้าเว็บจองปัจจุบันฝังรูปค่าบริการเดือนสิงหาคม 2026: [เว็บไซต์จอง](https://esports.computing.psu.ac.th/), [รายการเกม](https://esports.phuket.psu.ac.th/Services/our-games)

**ยังไม่ยืนยัน**: ตัวเลขราคาในรูปสิงหาคมเทียบกับข้อมูลในโปรเจกต์, สถานะว่างจริงของ Cockpit ณ เวลาที่ถาม, ปุ่ม Tab บนเครื่องศูนย์ที่อาจตั้งค่าใหม่ได้, กติกาแข่งขันฉบับอังกฤษที่อนุมัติ, ความถูกต้องของ GT ทั้ง 2,000 ข้อด้วยคน และผลทั้งชุดใน configuration หน้าเว็บที่เปิด LLM (ตรวจ API เพิ่มเพียงตัวอย่าง)

## ลำดับงานแก้ที่ตามมาจากหลักฐาน

1. เพิ่ม candidate ซ่อม **คำบอกงาน** ก่อน router และก่อน splitter ด้วยเพดานระยะห่าง/บริบท/การคุ้มครองชื่อเกม รหัสเครื่อง เวลา ตัวเลข และคำที่มีความหมายจริง; ถ้าหลายเจตนาใกล้กันให้ถามยืนยัน (`play`/`pay`)
2. ให้ live booking, price, control, penalty ตรวจทั้งข้อความเดิมและ candidate ที่ซ่อม **ก่อน** fallback เกม/ข้อมูลทั่วไป โดยเปรียบเทียบ evidence ของเจตนา ไม่ใช้ confidence คงที่ของหมวดเป็นหลักฐานว่าตอบตรงคำถาม
3. เพิ่ม test contract ที่ตรวจ **ส่วนประกอบทุกข้อ** ของคำถามสองเรื่อง และความสัมพันธ์เป้าหมาย–คำตอบ เช่น `Tab → Show Scoreboard`, `PS5 → ราคา + รายชื่อเกม`; แก้ heuristic status ของ no-answer/clarification แล้ว rescore รายข้อโดยไม่ลบผลดิบเก่า
4. แยก queue เจ้าของข้อมูล: เทียบตารางค่าบริการมกราคม/สิงหาคม, ตรวจปุ่มบนเครื่องจริง, อนุมัติภาษาอังกฤษของกติกาแข่งขัน, เตรียม fixture สถานะจองจริงตามเวลา ขั้นเหล่านี้ห้ามใช้การคาดเดาแทนหลักฐาน
5. หลังแก้ logic ให้รัน 239 regression IDs และ negative controls ก่อน จากนั้นรัน 2,000 คู่ใหม่โดยเก็บ output ชื่อใหม่ เปรียบเทียบทั้งคะแนนที่แก้เกณฑ์แล้วและความเปลี่ยนแปลง route/คำตอบ
