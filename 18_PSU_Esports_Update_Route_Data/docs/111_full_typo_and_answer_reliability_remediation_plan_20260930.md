# แผนแก้ความเข้าใจคำถามและความถูกต้องของคำตอบให้ครบวงจร

วันที่ 30 กันยายน 2026 · ฐานอ้างอิง r15 · สถานะ: แผนดำเนินงานจากหลักฐาน ยังไม่ได้เปลี่ยนโค้ดหรือนโยบาย

## 1. เป้าหมายและขอบเขตของคำว่า “แก้ครบ”

เป้าหมายคือให้แชทบอทเข้าใจคำถามไทยและอังกฤษที่พิมพ์เบิ้ล ขาด สลับแป้น กดแป้นข้างเคียง หรือผิดหลายจุด โดยยังตอบ “เรื่องที่ถาม” ครบทุกส่วน และไม่อ้างข้อมูลที่ยังไม่ยืนยัน ระบบต้องรู้ด้วยว่าเมื่อใดควรถามให้ชัดแทนการเดา โดยเฉพาะคำที่พิมพ์แล้วกลายเป็นอีกคำที่มีความหมายจริง เช่น play/pay

ความครบต้องตรวจแยก 5 ชั้น: (1) รับข้อความ/รักษาข้อมูลสำคัญ, (2) แยกจำนวนงานในประโยค, (3) เลือก intent/อุปกรณ์/ช่วงเวลา, (4) ดึงข้อเท็จจริงที่มีแหล่งและตอบครบ, (5) ประเมินผลด้วย ground truth ที่เชื่อถือได้ แต่ละชั้นอาจเสียต่างกัน การเพิ่มคลัง alias อย่างเดียวจึงไม่ครอบคลุม

ขอบเขตที่พิสูจน์ได้ในรอบพัฒนา: เพิ่มความทนต่อ typo ในชุดทดสอบและเคสใหม่ที่ไม่ใช้ปรับกฎ, ลดคำตอบผิดเรื่อง, และรักษาข้อห้ามเรื่องข้อมูลสด/ราคา/นโยบาย ขอบเขตที่ยังพิสูจน์ไม่ได้: “ถูกทุกข้อความของผู้ใช้จริง” และ “เครื่องว่างจริง” หากไม่มี booking fixture หรือ API สดที่พร้อมใช้ ข้อมูลจริงส่วนนี้ผู้ใช้ขอพักไว้ก่อน จึงไม่ใช้เป็นเงื่อนไขกีดกันงานอื่น

หลักคุ้มครอง: เก็บ raw input แยกจากข้อความตีความ; ไม่แก้รหัสเครื่อง เวลา วันที่ ตัวเลข จำนวนคน ราคา ชื่อเกมที่รู้จัก คำปฏิเสธ หรือชื่อเฉพาะด้วย edit distance; ไม่เขียนทับไฟล์ที่เจ้าของกรอกหรือ log เดิม; ไม่เปลี่ยนนโยบายเปิดบริการ/VR/maintenance/วันปิดพิเศษด้วยการคาดเดา; ไม่เอาคำแปลหรือข้อมูลจากแหล่งรองไปกล่าวว่าเจ้าของรับรองแล้ว

## 2. ฐานปัญหาที่ต้องวัดซ้ำ

ผล r15 จาก 2,000 คู่คำถาม (ไทย 1,000 อังกฤษ 1,000; clean + noisy รวม 4,000 การเรียกแบบ deterministic และปิด LLM/RAG fallback): clean ผ่าน 1,790/2,000, noisy ผ่าน 1,563/2,000, และ 239 ข้อเป็น clean ผ่านแต่ noisy ไม่ผ่านตามเกณฑ์ภายใน แยกจุดแรกที่ fail เป็น route 154, status 54, content 31 แบบผิดผสมสองจุดเกิด regression 82/400 เทียบกับเบิ้ล 26/400 ตัวเลขทั้งหมดเป็นผลเกณฑ์อัตโนมัติ ยังไม่ใช่จำนวนคำตอบผิดที่เจ้าของยืนยัน

ช่องโหว่ของตัววัด: 1,107/2,000 ไม่มี positive content contract; 120/239 regressions อยู่ในกลุ่มนี้; must_contain_any ใช้ OR จึงปล่อยคำตอบที่ตอบคำถามสองเรื่องเพียงเรื่องเดียวให้ผ่านได้; status บางชนิดเดาจากข้อความ/mode ผิด; live_lookup_required พิสูจน์การเข้าทางตรวจจอง ไม่พิสูจน์ว่าง/ถูกจองจริง; 72/84 ข้อต้นฉบับอังกฤษในกลุ่มกติกาแข่งขันคาดคำตอบที่ยังไม่มีคำแปลอนุมัติ; ทั้ง 2,000 ป้ายกำกับยังเป็น candidate/pending review

ตัวอย่างที่ใช้เป็น acceptance cases: ราคาของ PUBG กลายเป็นเรื่องย่อเกมเมื่อ “ราคาเท่าไหร่” เสีย; Cockpit “เครื่องไหนว่าบง้าง” ถูกตีเป็นคำถามเกม; PS5 ถามราคาและรายชื่อเกมแต่ตอบราคาอย่างเดียว; teporary suspension ไม่ได้กฎ; Tab buttno ใน VALORANT หลงไปยัง game detail; play/pay เป็นคำกำกวมที่ต้องถาม; Roblox ไม่พบแต่ตัววัดตีสถานะผิด ดู forensic รายข้อใน docs/110_typo_failure_forensic_and_scoring_20260930.md

## 3. Flow เป้าหมายจากข้อความถึงคำตอบ

ข้อความดิบ
  → ระบุภาษาและล็อกช่วงข้อมูลสำคัญ (ชื่ออุปกรณ์/เกม, รหัสเครื่อง, ตัวเลข, เวลา/วัน, negation)
  → สร้าง candidate เฉพาะคำบอกเจตนา/คำเชื่อมที่เสีย โดยเก็บข้อความเดิมไว้เสมอ
  → ให้คะแนน candidate จาก edit cost + แป้นใกล้ + บริบท + โครงประโยค + target + ความสอดคล้องกับความสามารถที่ระบบมี
  → กรณีชนะชัดใช้ candidate; กรณีความหมายจริงชนกันถามเจาะจง; กรณีหลักฐานไม่พอเก็บข้อความเดิม
  → แยกงานทุกส่วนของคำถาม (พร้อมพิกัด span จาก raw input)
  → route แต่ละงานตาม “สิ่งที่ผู้ใช้ขอทำ” ก่อน fallback ตามชื่อเกม/อุปกรณ์
  → ตรวจ precondition และแหล่งข้อมูล: สด/ตาราง/ราคา/นโยบาย/ภาษา
  → สร้างคำตอบพร้อมสถานะที่ชัด (ตอบได้, ไม่พบ, ต้องถาม, ข้อมูลสดใช้ไม่ได้, รอคำแปล)
  → ตรวจว่าแต่ละงานมีคำตอบและไม่มีข้อเท็จจริงที่ห้ามยืนยัน
  → ตอบพร้อมแหล่งและระดับการยืนยันที่เหมาะสม

การออกแบบนี้ไม่ให้ LLM เป็นผู้แก้คำผิดแล้วตอบเองโดยไม่มีการตรวจ fact และไม่ให้คะแนน confidence คงที่ของ route เป็นหลักฐานว่าความหมายถูกต้อง

## 4. รายการงานตามจุดเสีย

### 4.1 ซ่อมข้อความแบบ candidate หลายตำแหน่ง

ตำแหน่ง: app/core/normalization.py, app/core/keyboard_neighbor_recovery.py, app/core/multi_error_phrase_recovery.py, app/core/thai_transposition_recovery.py, app/pipeline/input_recovery.py, app/pipeline/preprocess.py

- แยก “ผิดในคำบอกเจตนา” ออกจาก “ผิดใน entity” และ “ข้อความดูแปลกแต่เป็นคำจริง” ตัวตรวจ n-gram ปัจจุบันเพียงร้องขอ intent review เมื่อผ่านเงื่อนไขความยาว/threshold; มันไม่แก้สะกด ต้องมี candidate generator เพิ่ม
- สำหรับไทย ทำงานระดับ grapheme/สระ/วรรณยุกต์ที่ยึดตาม Unicode cluster เพื่อไม่แยกสระนำ/ตัวสะกดผิดตำแหน่ง สร้าง candidate จากการเบิ้ล ลบ แทรก สลับตัว และระยะแป้นคีย์บอร์ดไทย พร้อมการตัดคำ/character n-gram เพื่ออ่านบริบทคำติดกัน สำหรับอังกฤษใช้ candidate จาก edit operations, keyboard map และ token boundary
- Candidate lexicon ใช้คำบอกงาน/คำเชื่อมจาก intent และ capability ที่ระบบรองรับ เช่น ว่าง, จอง, ราคา, เกมอะไรบ้าง, ปุ่ม, ระงับสิทธิ์, available, book, price, button, suspension; ไม่ทำรายการ alias ของทุกประโยค และไม่แก้ชื่อ target เป็นชื่ออื่นเพียงเพราะสะกดใกล้
- จำกัดพื้นที่ค้นหาและจำนวน candidate ต่อ span/ประโยค; จำกัด edit budget ตามความยาวคำ; รองรับหลาย typo ในประโยคเดียวโดย beam ขนาดเล็ก ไม่สร้างทุกการผสมจนช้าและไม่แก้คำที่ถูกอยู่
- เก็บ provenance ต่อ candidate: raw span, replacement, edit operation, keyboard distance, protected spans, rank, เหตุเลือก/ไม่เลือก เพื่ออธิบายข้อผิดใน trace และปิดการส่งข้อมูลส่วนตัวลง log เกินจำเป็น

### 4.2 ให้คะแนนและประตูตัดสินการซ่อม

ตำแหน่ง: app/pipeline/input_recovery.py, app/pipeline/semantic_intent.py, app/pipeline/target_lock.py, app/pipeline/ambiguity_gate.py

- คะแนนควรใช้หลักฐานหลายส่วน: ความใกล้ของตัวอักษร/แป้น, โครงประโยคไทย/อังกฤษ, คำรอบข้าง, intent ที่ต่อกับ target ได้, ความสามารถ/ข้อมูลที่ระบบมี, และคะแนนต่างระหว่างอันดับหนึ่งกับอันดับสอง
- ตั้ง hard veto เมื่อ candidate เปลี่ยนตัวเลข เวลา วันที่ รหัสเครื่อง ชื่อเกม/อุปกรณ์ที่ล็อกไว้ คำปฏิเสธ ขอบเขตกลุ่มผู้ใช้ หรือทำให้คำถามจาก “ทำได้ไหม” กลายเป็น “ทำไม่ได้ไหม” หากคำที่ได้เป็นคำจริงอีกความหมายและทั้งสอง intent เป็นไปได้ ให้ถามสั้น ๆ เช่น “ต้องการวิธีเล่น Moving Out 2 หรือค่าบริการครับ”
- แยก score สำหรับ “ข้อความนี้น่าจะพิมพ์ผิด” กับ “candidate นี้หมายถึง intent ใด” และ “คำตอบมีแหล่งข้อมูลพอไหม” อย่าใช้ route confidence ค่าคงที่ 0.95–0.99 แทนสามความหมายนี้
- ใช้ train/dev/holdout แยกตามต้นคำถาม ไม่ให้ clean/noisy ของเรื่องเดียวกันรั่วข้ามชุด ปรับ threshold บน dev และตัดสินจริงบน holdout รวม negative controls ที่คำคล้ายแต่ไม่ควรแก้ เช่น pay/play, จอย/จอง, เครื่อง/เกม และข้อความที่มี negation
- เงื่อนไข auto-correct: intent อันดับหนึ่งชัด, ไม่มี veto, ไม่เปลี่ยนคำถามมากเกิน edit budget, และมี answer path ที่รองรับ; หากไม่ผ่านให้ถามเจาะจงหรือ no-answer ที่ปลอดภัย

### 4.3 แยกคำถามหลายเรื่องหลังรู้โครงสร้างข้อความ

ตำแหน่ง: app/pipeline/engine.py (_split_multi_question และลำดับก่อน preprocess_input), app/pipeline/question_frame.py

- ปัจจุบัน splitter ทำงานก่อน preprocess จึงตกส่วน “แล้วมีเกมะไรบ้าง” ให้ย้ายขั้น candidate/การรู้คำเชื่อมเบื้องต้นมาอยู่ก่อน split หรือให้ splitter รับ raw + candidate spans พร้อมกันโดยไม่ทำลาย raw input
- แยกตามงาน ไม่ใช่แยกทุก “และ/กับ” เช่น “มี Call of Duty และ Fortnite ไหม” เป็นงานเดียวที่มีสองเกม แต่ “ราคาเท่าไหร่ แล้วมีเกมอะไรบ้าง” เป็นสองงาน
- ต่อคำตอบด้วย checklist ของแต่ละงาน: ราคา PS5 และรายชื่อเกม PS5 ต้องปรากฏทั้งคู่ หากข้อมูลส่วนหนึ่งยังรออนุมัติ ให้ระบุสถานะของส่วนนั้นแยก ไม่ถือว่าตอบครบ
- ทดสอบไทย/อังกฤษกับคำเชื่อมที่พิมพ์ผิด, typo ในทั้งสอง clause, ประโยคยาว, ประโยคที่มีเวลา/วันที่, และคำถามที่ตั้งใจเปรียบเทียบ ไม่ให้ split จนความหมายเพี้ยน

### 4.4 เลือก intent ตามกริยาที่ถามและ guard ก่อน fallback

ตำแหน่ง: app/pipeline/router.py, app/pipeline/engine.py, app/pipeline/protected_intents.py, app/pipeline/bilingual_english.py, app/booking/live_status.py

- ให้จุดถามที่จำเป็น (สถานะว่างตามเวลา, ราคา, ปุ่มควบคุม, กฎ/บทลงโทษ) ตรวจทั้ง raw และ candidate ที่ผ่าน gate ก่อน game detail/general fallback และเก็บเหตุผลว่าเลือก route ไหน
- ถ้าชื่อเกมหรืออุปกรณ์ถูกต้อง แต่คำบอกงานเสีย ห้ามสรุปว่าเป็นคำถาม “รายละเอียดเกม” อัตโนมัติ ตรวจว่าผู้ใช้ถามเรื่องราคา ปุ่ม เกมที่มี หรือสถานะจองก่อน กรณี PUBG/Tab ต้องตอบงานเดิม ไม่ให้ “มีข้อมูลของเกม” กลบความผิดเรื่อง
- Live booking: หากเห็นอุปกรณ์/ช่อง + เวลา + candidate ว่า “ว่าง/ถูกจอง/available” ให้เรียกตัวตรวจสถานะสดหนึ่งครั้งต่อคำถาม โดยคงช่วงเวลาและ resource เดิม ถ้า Dashboard/API ไม่พร้อม ต้องตอบว่า “ยังตรวจสถานะสดไม่ได้” ห้ามใช้เวลาเปิดบริการเพื่อกล่าวว่าว่าง ถ้าถามหมวดกว้างให้คืนจำนวนว่าง/ทั้งหมดและรายการแต่ละช่องเมื่อมีข้อมูลสดจริง
- กฎที่มีนัยนโยบาย เช่น temporary suspension ต้องคงถ้อยคำเงื่อนไขและช่วง 1–7 วันตามแหล่งทางการ คำผิดที่แก้ได้ต้องเข้า protected answer; หากหลักฐานคลุมเครือถาม/ปฏิเสธ ไม่สร้างกฎใหม่
- ตรวจ negative/OOD: “ไม่พบ Roblox ในรายการที่ยืนยันได้” เป็นคำตอบแบบไม่ยืนยันรายชื่อ; คำถามส่งเครื่องไปบ้านต้องไม่กลายเป็นคำรับรองว่าทำได้เพราะ route หลุด แม้ route อย่างเดียวผิดก็ควรซ่อมเพื่อความสม่ำเสมอ

### 4.5 ความครบและความถูกของเนื้อหา

ตำแหน่ง: app/pipeline/validator.py, app/pipeline/capability_registry.py, app/pipeline/bilingual_english.py, ตัวตอบเฉพาะเรื่อง และ source registry ที่เกี่ยวข้อง

- Answer contract ใน runtime ต้องตรวจข้อเรียกร้องจากคำถาม: จำนวนงาน, target, action, เวลา, เงื่อนไข, และความสัมพันธ์ระหว่างข้อเท็จจริง เช่น “Tab ใน VALORANT → scoreboard” มิใช่เพียงมีคำ VALORANT/Tab ที่ไหนก็ได้
- ให้สถานะ structured จากตัวตอบ: answer, clarification, no_answer, live_unavailable, localization_pending พร้อม source IDs และ coverage; renderer ค่อยแปลงเป็นภาษาไทย/อังกฤษ อย่าเดาสถานะจากประโยคที่แสดง
- ข้อมูลปุ่ม VALORANT ที่มี coverage_status=secondary_needs_manual_verify ตอบได้เพียง “ตามคู่มือแหล่งรอง Tab แสดง scoreboard; การตั้งค่าบนเครื่องศูนย์ยังไม่ยืนยัน” ห้ามยืนยันเครื่องจริง
- ภาษาอังกฤษ: ใช้ข้อมูล/คำแปลเฉพาะส่วนที่มีแหล่งและผ่านการอนุมัติ ถ้า game detail หรือกติกาแข่งขันยังไม่อนุมัติ ให้บอกสถานะนั้นอย่างตรงไปตรงมา แต่ typo ในคำว่า button ไม่ควรทำให้คำถามปุ่มหลงไปเป็น game detail แล้วแจ้ง pending อย่างผิดเรื่อง
- ตรวจค่าบริการ: app/calculator/service_fee.py ยังอ้างภาพมกราคม 2026 ในขณะที่หน้า booking ทางการฝังภาพสิงหาคม 2026 ต้องเทียบภาพ/ตัวเลข/วันที่มีผลกับข้อมูลที่ตอบ และให้เจ้าของยืนยันฉบับใช้งาน ก่อนแก้ราคาหรือ GT ใด ๆ ทุกคำตอบราคาควรผูก source version

### 4.6 ซ่อมตัวทดสอบก่อนใช้คะแนนเป็นตัวตัดสิน

ตำแหน่ง: tools/run_master_ground_truth_eval.py, tools/run_bilingual_2000_typo_eval_20260929.py, data/eval/master_gt_bilingual_multi_error_2000_20260929_r15.jsonl (อ่านเป็น baseline; เพิ่มไฟล์ revised แยก)

- สร้าง schema status แบบ typed จากผล pipeline และแยก clarification จาก answer; live_unavailable จาก live_availability_answer; not_found จาก answer; localization_pending จาก no_answer เพื่อไม่ให้ข้อความ “ไม่พบ Roblox” หรือ mode game_target_ambiguous ถูกจัดผิด
- เพิ่มสัญญา must_contain_all_groups/semantic relation/required subanswers และ forbidden claims เช่น ราคาต้องมีระดับกลุ่มผู้ใช้และแหล่ง, ถามสองเรื่องต้องตอบทั้งสอง, “เครื่องว่าง” ต้องมี live evidence, ปุ่มต้องสัมพันธ์เกม/ปุ่มที่ถาม คง must_contain_any สำหรับกรณี OR จริงเท่านั้น
- แบ่ง error tags อย่างน้อย: correction, split, route, status, missing subanswer, unsupported claim, stale source, translation pending, fixture unavailable, ambiguous synthetic edit, evaluator defect, latency; แยก “ผิดตามเกณฑ์” จาก “คนยืนยันว่าผิด”
- ทบทวน 239 regressions รายข้อก่อนเปลี่ยน expected label โดยเฉพาะ play/pay และคำถามที่ clean เองผิด; เก็บ label revision, reviewer, source, เหตุผล, วันที่ โดยไม่แก้ไฟล์ r15 เดิม สร้าง reviewed subset ที่ยืนยันแล้วและใช้เป็น release gate
- กรณี 72/84 กติกาอังกฤษต้องเลือกตามหลักฐาน: ถ้ายังไม่มีคำแปลอนุมัติ expected status เป็น localization_pending; ถ้าอนุมัติแล้วจึงวัดคำตอบอังกฤษ ห้ามนับข้อที่ยังไม่อนุมัติว่าเป็นความล้มเหลวของ typo engine
- อย่าใช้ HTTP 200 หรือ live_lookup_required เป็นผลว่าตอบว่าง/ถูกจองถูกต้อง ต้องมี fixture ผลจองที่รู้จริงสำหรับ open, booked, partial overlap, boundary, maintenance, special closure และหมวดกว้าง ไทย/อังกฤษ

### 4.7 เวลาในการตอบและความพร้อมของระบบ

ตำแหน่ง: app/pipeline/engine.py, runtime/API worker timeout, tools/run_supervised_bilingual_full_eval.py และ health check ของ Dashboard

- สืบ trace ข้อที่ใช้ 119.188 วินาที เทียบการรันซ้ำ 8.622 วินาที แยกเวลา preprocess, router, retrieval, LLM, network, serialization และ watchdog; ตั้ง timeout/cancellation ที่ API worker จริงพร้อมผลตอบที่ปลอดภัย ไม่ยืนยันว่า root cause คือส่วนใดก่อนมี trace
- รายงาน p50/p95/p99, timeout และอัตรา request ที่ต้องถามกลับ แยก deterministic, package API เปิด LLM, และ live booking; ทดสอบโหลดแบบที่ไม่รบกวน Dashboard ที่ใช้งานจริง
- Dashboard จาก start-dashboard.bat เป็น dependency ของสถานะสด ต้องแสดง health “พร้อม/ติดต่อไม่ได้” ให้ chatbot และผู้ดูแลเห็น พร้อมข้อความ fallback ที่ไม่แต่งสถานะจอง การทำให้รันต่อเนื่องเลือกวิธี deploy/service ภายหลังโดยพิจารณาเครื่อง Windows/สิทธิ์/การรีสตาร์ต/ความปลอดภัยกับเจ้าของ ไม่ผูกการตอบข้อมูลทั่วไปเข้ากับการเปิด Dashboard

### 4.8 กติกาบริการเดิมที่ต้องไม่ถอย

หลังปรับ pipeline ต้องรันชุด calendar/booking ไทยและอังกฤษซ้ำ: 12:00–13:00 ไม่เปิดให้จอง; ขอบช่วงเวลาเปิด-ปิด; Maintenance; วันปิดพิเศษ; VR 30 นาทีใช้ slot ชั่วโมงเต็ม (เช่น 09:00–09:30 นับครอง 09:00–10:00) คำตอบสถานะจองสดต้องไม่ใช้ตารางเปิดทำการแทนหลักฐานการจอง ห้ามแก้ booking_dashboard/center_schedule.json ซึ่งเจ้าของกรอกด้วยการเดา

|---|---|---|---|
| 0. ล็อกฐาน | เก็บ hash/commit ของ r15, fixture และรายงานเดิม; สร้างรายการ 239 ID พร้อมการจัดกลุ่ม; ร่าง evaluator schema ใหม่ | รายงาน baseline และรายการข้อที่ต้องคนตัดสิน | 2,000 คู่เดิม/รายงานเดิมยังอ่านได้ ไม่มีไฟล์เก่าถูกทับ |

## 6. ชุดทดสอบที่ต้องมีและเกณฑ์รับงาน

1. **Unit ของการแก้ typo:** เบิ้ล/ขาด/สลับ/แป้นใกล้/ผิดสองจุด ไทยและอังกฤษ; คำติดกันไทย; ตัวพิมพ์ใหญ่/เล็ก; ประโยคยาว; raw input คงเดิม; protected spans และ negation ไม่เปลี่ยน; candidate ambiguity ถามกลับ
2. **Intent regression:** 239 IDs เดิมแสดง clean/noisy ก่อนและหลัง พร้อม category/status/answer/source/trace; 210 clean failures แยกงานเดิมไม่โทษ typo; ข้อกำกวมที่ label ยังไม่ยืนยันไม่บังคับ auto-correct
3. **Compound answer:** ถามราคา+เกม, เวลา+จอง, ปุ่ม+เกม, นโยบาย+เงื่อนไข; ตอบครบทุกงานหรือชี้ชัดส่วนที่ยังตอบไม่ได้
4. **Live booking:** จำลอง fixture แบบว่าง, ถูกจอง, overlap, boundary, โซนมีหลายช่อง, API ล่ม; ตรวจข้อความที่ตอบจากข้อมูล fixture จริงและเวลาเดียวกัน หลัง user พร้อมให้ข้อมูลจริงจึงต่อการตรวจ end-to-end กับ WordPress
5. **Calendar/policy:** 12:00–13:00, VR 30 นาทีครองชั่วโมงเต็ม, Maintenance, วันปิดพิเศษ, ไทย/อังกฤษ; ราคา/กฎต้องผูกแหล่งฉบับที่ยืนยัน
6. **Bilingual/negative:** คำผิดที่ไม่ควรแก้และ OOD, play/pay, คำไทยใกล้แต่คนละเรื่อง, English localization pending; ไม่สร้างคำแปลหรือความสามารถที่ไม่มี
7. **Performance/package:** deterministic และ API จริงแยกตาราง; วัด p50/p95/p99; request ไม่ค้างเกินเพดานที่กำหนดโดยไม่มี fallback; ตรวจ health และ UI ของ package ใหม่โดยไม่รบกวนตัว r15 ที่เปิดอยู่

เกณฑ์ release ที่ตั้งได้ทันที: ไม่มีการเปลี่ยนตัวเลข/วัน/เวลา/รหัสเครื่อง/คำปฏิเสธโดยตัวซ่อม; ไม่มีคำตอบว่าง/ถูกจองเมื่อแหล่งสดใช้ไม่ได้; ไม่มีราคาหรือกฎที่แหล่งไม่ยืนยัน; reviewed subset ทุกข้อมีผล pass/clarification/known limitation พร้อมเหตุผล; ไม่มี clean case ที่เคยถูกต้องแล้วกลายเป็นคำตอบผิดซึ่งปล่อยผ่านโดยไม่ทบทวน; คำถามสองเรื่องต้องตรวจสองส่วน; ทุกการแก้เก็บผลใหม่แยกจาก r15

ไม่กำหนดเป้า “239 ต้องผ่าน 100%” เพราะบางข้อเป็นคำกำกวม/label defect/รอคำแปลหรือ fixture เป้าที่ถูกต้องคือ **ไม่มีข้อที่ยืนยันแล้วว่าผิดและยังไม่อธิบายหรือแก้**; ข้อที่แก้ไม่ได้ด้วยข้อมูลปัจจุบันต้องแจ้งสถานะที่ถูกต้องและไม่สร้างคำตอบเท็จ

## 7. สิ่งที่ทำเองได้ กับสิ่งที่ต้องการหลักฐานจากเจ้าของ

**ทำเองได้ทันที:** ซ่อม evaluator, ตรวจและติดป้าย 239 ข้อจากหลักฐานที่มี, เพิ่ม candidate/scorer/splitter/router/validator, เขียน negative controls, รัน 2,000 คู่และ API test แยกโหมด, ตรวจ latency, ทำ package r16 แยกพร้อม rollback, ตรวจแหล่งราคาอย่างอ่านอย่างเดียว และร่างคำแปลอังกฤษให้ตรวจ

**ต้องให้เจ้าของ/ผู้ดูแลยืนยันก่อนเปลี่ยนข้อมูล:** (1) ตารางค่าบริการที่ใช้จริง: ภาพมกราคมหรือสิงหาคม 2026 ฉบับใดมีผล และตัวเลขแต่ละกลุ่ม/โซนต่างกันหรือไม่? (2) กติกาแข่งขันอังกฤษ: ให้ข้อความใดเป็นฉบับอนุมัติ หรือให้คง localization_pending จนกว่าจะตรวจ? (3) การตั้งค่า Tab/ปุ่มอื่นบน PC ศูนย์ตรงกับคู่มือแหล่งรองหรือไม่? (4) เมื่อกลับมาทดสอบ booking จริง ต้องมี fixture ที่เจ้าของรู้ผลสำหรับช่อง/วัน/เวลาใด พร้อมสถานะที่คาดและเวลาบันทึก? ข้อ (4) ถูกพักตามคำขอเดิม จึงเดินงาน logic และ simulated fixture ต่อได้

**เรื่องการรันต่อเนื่อง:** หากจะเลิกเปิด start-dashboard.bat ทิ้งไว้ ต้องระบุเครื่องที่เป็น host, บัญชีที่ใช้รัน, เงื่อนไขหลัง reboot, ที่เก็บ secret/log และใครดูแลบริการ จึงเลือก Windows Service/Task Scheduler/process supervisor ได้อย่างเหมาะสม งานนี้แยกจากความเข้าใจ typo และไม่ต้องรอเพื่อแก้คำตอบทั่วไป
