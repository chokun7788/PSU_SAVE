# Flow สำหรับส่งต่อและใช้งานข้อมูลเก่า/ใหม่ — 2026-10-13

## เป้าหมาย

เจ้าของเพิ่มหรือแก้ข้อมูลผ่านฟอร์มที่มีตัวอย่าง ลูกค้าถามไทย/อังกฤษ แชทอ่านข้อมูลที่เผยแพร่และยังมีผล ครอบคลุมหัวข้อที่ขอ ตอบบริบทต่อเนื่องและทุกตัวเลือกเมื่อขอทั้งหมด ไม่ต้องเพิ่มชื่อเกมเป็นเงื่อนไขในโค้ด การทดสอบอัตโนมัติแยกจากการยืนยันข้อเท็จจริงของเจ้าของ

## เส้นทางหลัก

1. เจ้าของเลือกหมวด 24 หมวด → สร้างรหัสใหม่อัตโนมัติ หรือเปิดรายการเดิมด้วยรหัสเดิม
2. กรอกค่าที่ทราบพร้อมสถานะ known/unknown/not_applicable/conflicted, ชื่อไทย/อังกฤษ, ความสัมพันธ์, เวลา และการตรวจคำแปล
3. บันทึกร่างแบบ optimistic version: คนหรือโปรแกรมอีกตัวเปลี่ยนไปแล้วต้องให้โหลดฉบับใหม่ ไม่ทับ
4. ทดสอบร่างแยกจาก release จริง: อ่านร่างล่าสุดและแสดงป้าย DRAFT; ไม่เปลี่ยนคำตอบของลูกค้า
5. ตรวจข้อเท็จจริงและการอ้างอิง → อนุมัติเฉพาะ hash ของฉบับที่ตรวจ → เผยแพร่แบบ atomic
6. คำถามถัดไปอ่าน snapshot ใหม่; ชื่อเก่าพารายการไปข้อมูลฉบับใหม่; ข้อมูลที่ถอนหรือหมดอายุไม่ย้อนอ่านจาก legacy
7. สร้าง typed read state ต่อบทสนทนา เลือกเป้าหมายและหัวข้อใหม่ตามข้อความ รับคำตอบสั้นจากคำถามก่อน แต่เปลี่ยนเรื่องแล้วไม่สืบราคา/กลุ่มผิด
8. คำถามสถานะว่างใช้ live adapter; คำถามข้อมูลทั่วไปอ่าน published fields และ joins
9. การตีความชัดใช้ typed semantics; สำนวนใหม่ใช้ LLM เลือก fields ภายใน schema, ไม่สร้าง facts หรือ IDs
10. ตรวจ fields ที่ขอ สถานะ หลักฐาน เวลาและ release epoch; ขาดส่วนใดตอบส่วนที่ยืนยันพร้อมชี้ช่องที่ยังขาด
11. จัดภาษา/enum/เงื่อนไขให้อ่านได้; รวมรายการเกมใหม่กับ legacy โดยไม่ซ้ำและไม่ฟื้นรายการที่ถอน
12. บันทึกเหตุผลเลือก คิว timeout และ coverage ใน log ใหม่ ไม่แก้ log รอบเก่า

## ลำดับตรวจทานที่ลงมือ

| รอบ | จุดตรวจ | การแก้จากหลักฐาน |
|---|---|---|
| 1 | เพิ่มรายการหลายตัว, เปลี่ยนชื่อ, บริบทถามต่อ, preview | แม่แบบรหัสซ้ำ → รหัสใหม่; typed state; ชื่อเก่าตาม revision; ทดสอบร่าง |
| 2 | ข้อมูลเก่า+ใหม่, relation ราคา, ถามงบ | รายการเกมรวม; ราคา resource→service→rate; ไม่ขยาย fixed/free/unknown; งบหลายคนไม่ใช้ราคาคนเดียวแทน |
| 3 | การแยกเวลาเล่นกับราคา, compatibility | ถอด rate ออกจาก scope ทั่วไป; เปิด rate schema เฉพาะราคา; draft preview รักษาสัญญาเดิม |
| 4 | ตัวรัน/ภาษา/แพ็กเกจจริง | พบ cold GPU request timeout; warm model ก่อนรับคำถาม; บริการโมเดล+คลังโมเดลของแพ็กเกจ; source fingerprint; long-path copy |

แต่ละรอบมี log ก่อน/หลัง ไม่ใช้คำว่า “ตรวจผ่านครบ” จากจำนวนรอบ หรือจาก HTTP 200 อย่างเดียว รายงานผลจริงรวมใน RESULTS_TH.md

## กรอบประเมินแยก

- schema/source: ค่าที่อ่านตรง revision, evidence pointer และสถานะครบ
- intent: expected fields จากชุดคำถามที่กำหนดก่อนรัน ไม่ใช้ fields ที่ระบบเลือกมาเป็น gold
- เนื้อหา: ค่า/จำนวน/เงื่อนไขปรากฏจริง ไม่รับเพียงมี field ใน trace
- ภาษา: คำแปล enum ไม่ต้องแสดง raw code; ต้องความหมายตรง ไม่แต่ง business facts
- conversation: ข้อมูลใหม่ระหว่าง session และการเปลี่ยนเรื่องไม่ค้าง revision/หัวข้อเก่า
- runtime: API ติดต่อสำเร็จ, model generate สำเร็จ, schema ถูก, semantics ถูก และคำตอบถูก แยกเป็นคนละขั้น
- production package: ไม่มี logs/tokens/DEMO DB; ไม่พึ่ง Python/Ollama ของเครื่องนักพัฒนา; ตรวจ model digest และ archive CRC
- owner factual review: ให้เจ้าของยืนยันข้อเท็จจริงที่ยังไม่ทราบ ไม่ใช้ผล fixture เป็นการอนุมัตินโยบาย
