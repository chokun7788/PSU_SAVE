# ตรวจข้อมูล WordPress จริงและคำถามจากแชท — 29 กันยายน 2026

## สิ่งที่ตรวจได้จากต้นทาง

ตรวจ ณ ประมาณ 14:42 เวลาไทย โดยดึง `wbk_appointments.csv` และ `wbk_services.csv` จาก WordPress โดยตรงในหน่วยความจำ แล้วเทียบ hash ของไฟล์เดียวกันกับ Booking Dashboard ที่แชทบอทใช้อยู่ (`127.0.0.1:8091`). CSV มี 3,175 แถวจองและ 18 บริการ; Dashboard ระบุ `remote_csv_live` และ hash ตรงกับการดึงโดยตรงทุกวันที่ตรวจ. เครื่องนี้ไม่ได้เปิด Dashboard ต้นฉบับบน D: ที่พอร์ต 8080; แพ็กเกจแชทบอทเปิด Dashboard ที่พอร์ต 8091 เอง. `center_schedule.json` ของ D:, โปรเจกต์ และแพ็กเกจเหมือนกันทุกไบต์; `server.py` ของ D: กับแพ็กเกจต่างกันเพียงข้อความอธิบายและ endpoint `/health`.

ใช้ [ตัวตรวจอิสระ](../tools/audit_live_booking_csv_20260929.py) คำนวณจำนวนจองที่ทับแต่ละช่องชั่วโมงจาก timestamp และ status ของ CSV แล้วเทียบกับ `/api/chatbot-status`. ผล [รอบ 6 วัน](../reports/live_booking_real_csv_audit_20260929_calendar6.json): 756 ช่องรายเครื่อง, 153 ช่องมีรายการจอง, 279 ช่องไม่มีรายการจอง, 324 ช่องปิด, **ไม่พบผลต่าง**. วันที่ตรวจคือ 16, 29, 30 กันยายน และ 2, 3, 5 ตุลาคม 2026 ครอบคลุมวันปกติ พัก 12:00–13:00, Maintenance เช้าวันจันทร์, Maintenance บ่ายวันศุกร์ และวันเสาร์ปิด. ตัวตรวจไม่บันทึกชื่อ อีเมล เบอร์โทร ID ผู้จอง หรือแถว CSV ดิบ.

นี่เป็นการยืนยันว่า **Dashboard อ่าน CSV และคำนวณช่องรายชั่วโมงตรงกับ CSV ณ เวลาตรวจ**. ยังไม่ใช่หลักฐานอิสระว่าหน้า WordPress อนุญาต/ห้ามจองทุกช่องตามนโยบายที่เจ้าของต้องการ และผลสดอาจเปลี่ยนเมื่อมีการจองใหม่.

## คำถามจากบทสนทนาและ log รุ่นก่อน

บันทึก web chat รุ่น r8 มี “สวัวสดี” และ “สวะสดี” ซึ่งเคยเข้าทางถามกลับ; เมื่อนำคำเดียวกันมาถามรุ่นล่าสุด ได้คำทักทาย. ตัวอย่างสะกดผิดจาก log เช่น “PS5 ราคารเท่าไหร่”, “เปิดกี่โมว”, “จองย้งไง”, “มีเกมอาไรบ้าง” และคำที่ใช้พัฒนารอบก่อน (“มีเกมแข่งรดไหม”, “ขอบคุนคับบบ”, “เพลย์ห้าคิดตังเท่าไหรอะ”, “มีไรเล่นมั่ง”) เข้าหมวดที่ตั้งใจและตอบจากข้อมูลของศูนย์. Log ระบุ `channel=web` แต่ไม่บอกว่ารายการใดเป็นผู้ใช้จริงหรือการทดสอบ จึงไม่ใช้จำนวน log เป็นอัตราความแม่นยำของผู้ใช้จริง.

พบข้อผิดจากข้อความที่เจ้าของยกในบทสนทนา: “วันนี้ตอน10โมง PC1 ว่างไหม” และ “พรุ่งนี้ตอน10โมง PC1 ว่างไหม” ถูกตัวกรองแป้นพิมพ์ของเว็บปฏิเสธก่อนเรียกข้อมูลจอง. ตัวตรวจอ่าน “โมง” เป็นปุ่มอังกฤษ `F,'` และให้คะแนนผิดภาษา 0.548 ทั้งที่ข้อความไทยอ่านได้. แก้ที่ `app/core/keyboard_input_anomaly.py` ให้หลักฐานการแปลงที่ **ไม่ใช่คำอังกฤษที่รู้จัก** และแทบไม่ได้คุณภาพเพิ่มมีน้ำหนักต่ำลง. หลังแก้และเปิดแพ็กเกจใหม่ คำถามแรกตอบว่าช่วง 10:00–11:00 วันนี้ **ไม่มีรายการจอง** (เป็นเวลาอดีต ณ ตอนถาม) และคำถามพรุ่งนี้ตอบว่า PC #01 **ว่าง**; ทั้งคู่ตรง CSV. ข้อความผิดแป้นพิมพ์จริง `g]jo` ยังถูกขอให้พิมพ์ใหม่.

ชุดประเมินตัวกรอง 500 ข้อรันก่อน/หลังได้ผล test layout เท่าเดิม: TP 192, FP 0, FN 0; repeat TP 140, FP 1, FN 20. ผลอยู่ใน `reports/keyboard_input_anomaly_eval/20260929_before_pc1_fix` และ `20260929_after_pc1_fix`. Smoke test ตัวกรองและ booking status ผ่าน. ผลนี้วัดชุดสังเคราะห์ที่มี ไม่ใช่หลักฐานว่าตัวกรองจะไม่พลาดข้อความผู้ใช้รูปอื่น.

## ข้อที่ต้องให้เจ้าของศูนย์ยืนยัน

1. **สถานะ `pending`**: วันที่ 30 ก.ย. CSV มี 27 รายการ `pending`; Dashboard นับเป็นช่องไม่ว่าง. `pending` ใน WordPress ของศูนย์หมายถึงล็อกช่องทันทีจนกว่าจะยกเลิก/หมดอายุใช่หรือไม่? ถ้าไม่ใช่ ต้องระบุกฎสถานะที่จองได้และเวลาเปลี่ยนสถานะก่อนแก้ตัวนับ.
2. **VR 30 นาที**: CSV วันที่ 29 ก.ย. มี VR Morning 30 Mins ที่ 10:00, 10:30, 11:00 และ 11:30 เป็นคนละรายการ ซึ่งแสดงว่า WordPress รับช่อง 30 นาทีติดกันได้. Dashboard/แชทบอทสรุปแต่ละชั่วโมงว่าไม่ว่างเมื่อมีรายการ 30 นาทีทับ. ที่เคยบอกว่า “30 นาทีให้นับกินชั่วโมงเต็ม” ต้องการใช้กับ **คำตอบของแชทบอทอย่างเดียว** หรือจะให้ **ระบบจอง WordPress ห้ามจองอีก 30 นาทีในชั่วโมงเดียวกัน** ด้วย? คำตอบสองแบบนี้ส่งผลต่อนโยบายจริงต่างกัน.
3. **วันปิดพิเศษ**: `dates` ใน `center_schedule.json` ของ D: ยังว่าง. หากมีวันปิดพิเศษจริง ขอวันที่และสถานะเช้า/บ่ายที่เจ้าของยืนยันเพื่อทดสอบกับวันนั้น; รอบนี้ยืนยันได้เฉพาะ Maintenance ประจำสัปดาห์และวันเสาร์ปิด.

ไม่ได้แก้ไฟล์ตารางเวลาที่เจ้าของกรอก ไฟล์ CSV ต้นทาง หรือ log เดิม. การถาม API เพิ่มรายการใหม่ท้าย log ตามการทำงานปกติ.
